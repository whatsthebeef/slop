# Slop — Behaviour & Architecture Spec

Oct 2, 2026 · @John

## Overview

Slop replaces a team's separate planning tool and issue tracker: it owns planning, the board, shared records and the agent system, and exposes endpoints (MCP and REST) that implementation tools pull from and push to. This document is authoritative for slop's lifecycle, contracts and rules; the sessionator document is authoritative for local command behaviour.

- **Slop** turns any input into a plan, manages globs on the board, tracks PRs, commits, builds, tests and deployments, and produces time reports.
- **Implementation** is done by Claude Code routines for subs and sames, and by sessionator (or any equivalent developer tool) for supers. Sessionator keeps workspace management (tmux, worktrees, branches); agent management moves into slop.
- **Planning has no repository access.** Slop captures intent; the implementation system investigates the code.
- **Hexagonal architecture.** A framework-free `core/` holds the glob domain, rules and prompts. Everything external (MCP, REST, GitHub, CodeBuild, storage, LLM, notifications) is an adapter behind a port. A lint rule forbids the core importing adapters.
- **Writes go through the core; reads can come straight from the store.** Every change, from any entry point, calls the same application services.

**Project profiles (genericity):** everything project-specific is per-board configuration, not code: the list of environments (each glob's environment is chosen at creation or pick-up); optional integrations (CodeBuild results, deploy tracking, ATF), whose indicators and checks only appear when enabled; sensitive paths; routine prompts; which labels apply. Anything reporting as a GitHub check run works for any project. No project's environment names, integrations or conventions are hard-coded in slop or its public repo; each board's profile and knowledge are entered in slop, and slop's own development runs as a board with a sparse profile.

## Globs

A glob is one unit of work on a board. It has a slop type (how the work flows) and a category (what the work is, for time tracking).

**IDs** are `s<board><type><n>`: `s1f1` feature, `s1t1` task, `s1b1` bug, `s1h1` hotfix, `s1k1` knowledge-base item. Each board has an atomic counter per type; creation is a conditional write, so a collision errors instead of overwriting. IDs are immutable: the letter reflects the category at creation, even if the category later changes. Hotfixes are deferred; the h type is reserved only.

**Slop types**

- **Sub:** small bug fixes and minor UI/UX tweaks. The input is the plan. Implementation starts automatically and merges to master without human review if the sub review passes.
- **Same:** standard non-pairing tasks. Planned by loading the glob with context (plan.md, meeting notes, Slack threads, designs). Triggered manually unless the input says otherwise. PRs are merged by the developer once satisfied with the reviews and results. A routine can optionally implement a same (chosen at creation or pick-up).
- **Super:** PO + developer pairing. In Doing on creation; the developer implements and marks the glob's draft PR ready for review; sessionator maintains the glob's implementation record.

**Categories:** features are RnD; tasks and bugs are maintenance.

| Category | Sub | Same | Super |
| --- | --- | --- | --- |
| Feature (RnD) | No | Yes | Yes |
| Task (maintenance) | Yes | Yes | Yes |
| Bug (maintenance) | Yes | Yes | No |

The matrix is a core invariant. Sub-to-same conversion is always valid.

**Group** is a plain string attribute, given in the MCP message or inferred by slop from the input. Inference prefers existing group names. Names are normalised for matching; the label colour is derived from a hash of the name.

**Start after (`after`):** a glob can wait for other globs on its board to merge. `after` is the list of their IDs, set at creation (`create_glob`'s `after`, the New glob form's "Start after", `slop new --after`, `sstor --new --after`) and editable in the glob view while the glob has no branch (`update_glob`'s `after`). IDs must exist on the board and can't make a cycle (through `after` and the holds below); IDs that have already merged are ignored (dropped when set). What the glob still waits for is derived from the live state of those globs, not stored: a dependency is *merged* once it is Reviewing or Signed off (a super that merged with Merge and continue is still open); one that is deleted, or went back to Planning, still counts as unmerged, and the glob shows that ("`<id>` was deleted; waiting") and stays put. Stored on the glob with it: `after`, `impliedAfter` (holds from the board's merge policy: `{ id, paths, overridden? }`, see Knowledge), `waiting` (`{ since }` while the glob is held in Planning for them) and `clash` (a warning, see Merging). `get_glob` and the glob view add `waitingFor` (each unmerged dependency with the reason) and `waitedOnBy` (globs in Planning that wait for it). The card shows "after s15t7" (or "waits for s15t7" with the exclusive-path reason on hover), each ID linking to that glob, and "clashes with s15t7" while `clash` is set; the glob view lists what it waits for and what waits for it, offers the `after` field while the glob has no branch, and Start anyway (the board also offers it as a move from Planning).

**Sign-off labels** FR (Functional Review), CR (Code Review) and QA are set to Required automatically when a glob moves to Reviewing: subs get QA, sames and supers get FR, CR and QA. After that, only humans change them. Each label has three states and carries a review checklist: **Required** (waiting for the reviewer, initially and whenever the developer resubmits), **Added** (the reviewer added checklist items for the developer to work through) and **Approved** (the reviewer is satisfied, with or without items). The reviewer either submits one or more items (Required → Added) or approves (Required or Added → Approved); the developer ticks and unticks items while the label is Added and resubmits it for review at any time, even with items unticked (Added → Required, items and ticks kept). Items are never removed, so each review round adds to the same list; once the glob is signed off they are read-only. An approved label can be re-opened (→ Required). Anyone on the board may act on a label for now. The card shows each label as a coloured chip (Required outlined brown, Added clay, Approved green) with a popover for a quick Approve or Re-open; the glob view holds the checklists. The glob lights up when its last label is approved. Who did what and when goes in the event log.

Labels only appear on a card once the glob is merged (Required, Added or Approved).

**plan.md is created with the glob:** `create_glob` (MCP, REST, CLI `slop new`) stores plan.md v1 verbatim, from `plan` if given, else the summary as given, else the intake input, with provenance (human for REST, sessionator for MCP, and the actor). The summary is left as it is. Agents rewrite plan.md with `save_plan`, not `update_glob`. Globs created before this have no plan.md artifact until one is saved; `get_plan` and `get_context` show their summary as version 0.

**Artifacts** (plan.md, the implementation record, local review.md, context attachments) live in slop as versioned records with glob ID, type, version, commit SHA where relevant, and provenance (human, sessionator, or model + prompt version). Binaries go to S3; the glob holds references.

**Implementation plan:** the implementing tool (routine, sessionator or equivalent) generates an implementation plan as an artifact on the glob, with an amendments section. Edits to plan.md after triggering are allowed; the run simply continues, with no lock or special state.

## Board and lifecycle

Globs move through four lists: Planning, Doing, Reviewing, Signed Off. Reviewing means merged to master and awaiting human sign-off; PR review happens while a glob is in Doing.

|  | Planning | Doing | Reviewing | Signed Off |
| --- | --- | --- | --- | --- |
| Sub | Skipped | Automatic on creation; routine starts | Automatic when sub review passes and it merges; QA Required | Automatic when all labels are Approved |
| Same | Starts here | Start button or pick-up (glob view or sstor); a routine runs if chosen | Automatic when the developer merges the PR; FR, CR, QA Required | Automatic when all labels are Approved |
| Super | Skipped | On creation | Automatic when the developer merges the PR; FR, CR, QA Required. Merge and continue lands work mid-way and keeps the glob in Doing | Automatic when all labels are Approved |

**Moves** happen through buttons in the glob view, enabled only where a manual move makes sense. **Type changes** are buttons in the same row, shown only for the changes `changeFields` would accept now (`allowedTypeChanges`): *Make it a sub* (a routine run starts now, or after what it waits for, and it merges itself; it confirms first, and for a feature offers *Make it a task sub*, which sets the category and type together), *Make it a same* (a person merges it) and *Pair on it* (a super; no routine run). The type is a label beside the status, with the reason no change is possible as its tooltip. Category stays a select offering only what the type allows; it saves on change, shows *Saved* with Undo, and a refused save keeps the old value and shows the reason. Everything else is driven by events, including human events outside slop (a developer merging a PR in GitHub). Manual and automated moves go through the same core transitions.

**Failures:** a failed or timed-out run stays in Doing with a failed flag. No automatic retry.

**Sub to same conversion** happens when the sub review flags the change; the branch, work and PR are kept, and the developer merges it once satisfied. A sub whose rebase hits a conflict does not convert: it stays in Doing as failed, and the planner finds a human implementer.

**Start again** returns a glob to its starting status (sub: Doing with a new routine run; same: Planning; super: Doing with its creator), closing its PR and deleting its branch (a sub or super is re-provisioned at once; a same gets a new branch when it next starts); see the transition table for everything it resets. **Delete** shows a strong warning, then removes the glob, its branch, its S3 artifacts and its events (so its time leaves the reports). No archive.

**Signed Off** globs drop off the board after 2 weeks (computed on display) and remain in a paginated list view.

**Card display:** small visual differences per slop type with filtering; group label; FR/CR/QA switches; artifact icons (plan, implementation record, commits, local review, remote review, tests, deployments) that open the relevant view; planner shown until a human implementer picks it up, then the implementer; failed flag; deployment indicators for release environments; a colour that shifts from neutral to amber to red as the glob passes 2 calendar days in Doing without merging, plus a "PR still draft" indicator.

**Routine run on the card:** a run indicator shows the current run's state (queued, active, watching, ended: completed, failed or superseded), its routine owner and triggerer, when it started and when it last made progress (its last slop call or push). The glob view lists the run history and, for the current run, an *Open in Claude* link to the cloud session at claude.ai/code and a copyable *Continue locally* command (`sstor --teleport <id>`). Slop stores each run's cloud session ID and URL from the routine fire response (to verify in slice 4; fallback: the routine reports them on its first MCP call). Only the routine owner can teleport into a run; for everyone else the link is view-only.

**Live updates:** every save publishes a small hint (`kind`, `globId`, `version`) through the notifier port. The server streams it to every open board over server-sent events; the board refetches that glob (unless it already holds that version), and reloads the whole board after reconnecting. The exception is `glob.artifacts`, sent when an artifact is added: artifacts are versioned on their own and the card reads them from the artifact records, so adding one doesn't bump the glob's version (which would turn concurrent client writes into conflicts), and its hint carries no version; the board always refetches that glob, and any open artifact view. Each glob carries a version number and every write is conditional on it, so simultaneous moves resolve cleanly.

**Changing type, category and group:** category and group can be changed at any time (the type/category matrix still applies; IDs keep their original letter). Type changes are limited to what the current execution mode supports: sub to same at any point before merge (the developer then merges instead of auto-merge); same and super interchangeably in `planning`, `in_progress` or `pr_open` with no run queued, active or watching (a super in Planning offers Pick up but not Start, and picking it up moves it straight to Doing as in row 6; switching back restores Start); same to sub only from `planning`, which is a transition (row 26) and starts work. No other type changes are allowed, and apart from row 26 a type change never moves the glob. Reports use the category at report time.

## State machine

The core tracks a status per glob; the four lists are a projection of it, and every move, manual or automatic, is one of the transitions below.

| Status | List | Meaning |
| --- | --- | --- |
| `planning` | Planning | Same being planned; nothing running |
| `implementing` | Doing | A routine run is working on the glob |
| `in_progress` | Doing | A human is implementing (supers, or a picked-up glob) |
| `failed` | Doing | A run failed, timed out, hit a merge conflict, or its PR was closed unmerged |
| `pr_open` | Doing | The PR is ready for review, awaiting the sub gate or the developer's merge |
| `merging` | Doing | Slop is rebasing, rerunning checks and squash-merging |
| `reviewing` | Reviewing | On master, awaiting FR/CR/QA sign-off |
| `signed_off` | Signed Off | All required labels Approved |

**Rules across all transitions**

- Every command and event loads the glob's current state and is checked against this table; anything not listed is refused.
- Writes are conditional on the glob's version, so simultaneous events resolve cleanly.
- Changing type, category or group is not a transition: it never moves the glob, only changes which rows apply next.
- Draft PRs are recorded on the glob without changing status.
- Sub policy (rows 11–13): a sub is evaluated against the board's policy as soon as it enters `pr_open`; its checks are not awaited. The `checks` workflow also runs on every push to the base branch, which is how a red base (and a sub that caused it, row 16b) is found.
- Time attribution follows the planner until a human implementer picks the glob up, then the implementer; triggeredBy only chooses whose routine runs.

**Provisioning and reliability**

- **Provisioning:** a glob gets its branch, empty first commit and draft PR when it enters Doing: at creation for subs, supers and auto-started sames; on Start or Pick up for a same in Planning. Planning stays free of GitHub, and nobody can work on a branch before the glob is started or picked up. Provisioning is queued before any routine run, and a routine is only fired once its glob is provisioned. `create_glob` takes an idempotency key and returns once provisioning has been attempted (`provisioning: none` for a same in Planning). If GitHub fails, the glob is still saved with a provisioning-failed flag and the response returns its ID and provisioning status, so a retry with the same key never creates a second glob; a background job retries, and sstor reports the problem instead of checking anything out. A 404 or 403 from the code host is not retried: the glob's `failure` (kind `provisioning`) says why and how to fix it (install the App on the repo, or add `contents: write`), its queued run ends with the same reason, the card and glob view show it first, and the board's bar warns "slop's GitHub App can't access <repo>" (source `repo-access`) until the next successful code host call for that repo. Other failures retry with backoff, and the last attempt records the failure the same way.
- **Routine runs** have their own lifecycle, independent of the glob's status: queued → active (the routine has called slop) → watching (its PR is ready and auto-fix is running) → ended (completed, failed, superseded). A queued run that makes no slop call within the board's start time (default 30 minutes) never started: it is failed with the reason "Routine run never started (queued at `<time>`)", and the card shows that reason with the run's session link and Start again. While it is queued the card shows how long once that passes 10 minutes ("Routine run queued for 25 min: open the session"). Runs that never start count toward the board's routines readiness item when it repeats (two recent failures). A run ends when the glob is merged, picked up, taken over, started again, closed or deleted. Each run has a run ID, passed in the fire payload and returned with its artifacts and `report_failure`; results carrying a superseded run ID are recorded but ignored.
- **Generation:** each glob has a generation number, increased by re-trigger, take over and start again. Every outbox job carries the generation it was queued under and is re-checked before it executes; jobs from an older generation are cancelled.
- **Commit-specific results:** check, review, build and ATF results are tied to a commit SHA; results for commits that are no longer the branch head do not drive transitions.
- **Deduplication:** GitHub deliveries are deduplicated by delivery ID, other webhooks by their source event ID. Incoming events are applied against the glob's current version inside the handler; only client writes carry an expected version.
- **Outbox:** side effects (firing routines, GitHub provisioning, CodeBuild deploys, `release_waiting` after a merge, `check_exclusive_paths` after a push) are written to an outbox table in the same transaction as the state change and executed by the job queue with retries and idempotency keys, so partial failures resume.
- **Routine ownership:** slop stores `triggeredBy` and `routineOwner` separately. `triggeredBy` chooses whose routine runs; commits, PRs and Claude usage belong to the routine owner (e.g. the board's default routine owner on fallback); time follows the planner until a human picks the glob up.
- **Routines and humans (cooperative):** pick-up is refused while a run is active or watching; Take over supersedes it. Routines check the glob through the MCP before every push and stop if their run is superseded, a human implementer is recorded, or the glob is merged. Because the check and the push are separate operations, a late push is still possible: routine commits carry a `Slop-Run: <runId>` trailer, and a push from a superseded run is flagged on the glob so the developer can revert it. Slop deletes any glob branch recreated by a late push after merge (to `reviewing`; a super's Merge and continue keeps its branch, row 31).

**Flags shown alongside status** (not states): failure reason, ATF failure, deployment state per environment, aging colour, "PR still draft".

**Domain events** written to the log: `GlobCreated`, `FieldsChanged`, `StatusChanged` (from, to, actor), `RunTriggered`, `RunFailed`, `BranchCreated`, `CommitPushed`, `PROpened`, `PRReadyForReview`, `PRClosed`, `SubReviewCompleted`, `ReviewReceived`, `Merged`, `MergeFailed`, `LabelChanged`, `LabelItemTicked`, `PickedUp`, `ArtifactAdded`, `DeployRequested`, `DeployReplaced`, `DeployStarted`, `Deployed`, `DeployFailed`, `BuildCompleted`, `ATFCompleted`, `GlobDeleted`.

**Run failure detection (row 17)** uses both mechanisms: the agent calls `report_failure` when it recognises a failure, and slop fails a run that shows no progress (no slop call or push) for a per-board number of hours (default 2), or that has not marked its PR ready within a longer per-board limit (default 8 hours). A watching run (auto-fix) is idle by design, so it has **no no-progress limit**: a watcher on a PR whose head checks pass or are pending is never failed for being quiet. It is failed only for not responding: when the head's checks fail (not inherited from the base) the clock starts, and a watcher that makes no slop call or push within the board's response window (`runRespondMinutes`, default 30 minutes; counted from the failure or the run's last call, whichever is later) is failed with the reason "Auto-fix didn't respond to failed checks (`<check>`) on `<sha>`". The glob stays in pr\_open, the card shows that reason, and offers **Retry auto-fix** (row 25a) beside Pick up. **One automatic retry:** the first time a watcher gives up this way, slop does the Retry auto-fix itself instead of showing the failure: a new routine run on the same branch and PR at the same generation (marked as the automatic retry, so a person sees both runs in the history), whose fire text carries the failure summary (the failing check's name, step and first lines). Only when that run also ends without fixing the PR does the card show the reason and the **Retry auto-fix** button. A run that reports another failure itself, a super, and a glob with a human implementer are not retried automatically. Review comments aren't tracked by slop yet, so an ignored comment doesn't start the clock. Watching ends when the run ends. The routine's session must subscribe to the PR's activity after `mark_ready`; the orchestrator's Auto-fix section says how.

## Contracts

Slop has four kinds of interface: MCP tools for agents and the Claude app, REST for the board, inbound webhooks and events, and outbound calls. All of them call the same application services and enforce the same state machine and role rules.

**Common rules**

- **Auth:** the board uses a server-side session after Cognito login; MCP and REST accept Cognito access tokens, so every call acts as a real person with their board role; webhooks and ingest are verified by per-integration secrets or signatures.
- **Versions:** every client write to a glob carries the version it read; a stale version returns a conflict with the current glob. Exceptions: put\_artifact and report\_failure are append-style records guarded by run ID (for routines) rather than glob version, since artifacts are versioned on their own and a failure report must not be lost to a concurrent edit.
- **Errors:** `forbidden` (role), `not_found`, `version_conflict`, `invalid_transition` (with current status and allowed actions), `invalid_combination` (type/category matrix).

## Implementation and agents

Subs and sames are implemented by Claude Code routines owned by whoever triggered them; supers are implemented by the developer through sessionator or an equivalent tool.

**Routines**

- Each developer creates one routine in their own claude.ai account, used for both subs and sames, from a shared prompt and command. The prompt stays thin and identical: fetch the glob from the slop MCP and follow its instructions using the agents in `.claude/`.
- Each developer stores the routine's fire URL and token in Secrets Manager at `slop/routines/<userId>`; slop builds the path from the triggerer. If the triggerer has no routine, slop falls back to the board's default routine owner.
- A routine's cloud environment has a fixed set of repositories, so a developer can also store one routine per board (`slop/routines/<userId>/<boardId>`, as Secrets Manager names can't hold `#`; locally `<email>#<boardId>` in `.routines.json`), used before their default. Either way the routine's environment must include the board's repository, with the Claude GitHub App installed on it. The fire text names the board's repository, and a session that doesn't have it, or can't push to it, reports a failure instead of working in another repository.
- The triggerer is the person whose session created the glob, where slop can determine it.
- Usage, the daily run cap, commits and PRs belong to the routine owner; time follows the planner until a human picks the glob up (slop stores both). Only the routine owner can teleport into a run.
- Sessionator's sstor --routine-setup command handles routine setup and storing the secret.

* **Seats:** every Team seat includes Claude Code according to Anthropic's help center; Premium seats add higher usage. Standard-seat users can own routines but will hit limits sooner.

**Agent system**

- **The agent set is board knowledge.** Each board's agent definitions, commands, hooks and Claude settings are KB items (kinds `agent`, `command`, `hook`, `settings`, `mcp`, `claude_md`), versioned and changed through approved proposals like any other document. The board's **agent-set version** increases with every approved change to any of them, and whenever the catalog's agent set changes.
- **Catalog origin, layered:** a board's agent set is slop's generic agent set (`catalog/agents/` in the public repo) with the board's own layer on top, so catalog changes reach every board without anyone merging. A board row is either an **overlay** on a catalog file, kept separately and appended under `## Board rules` (markdown files) or deep-merged as JSON (`settings.json`: objects merge, arrays concatenate without duplicates, board values win), or a whole **file** the board owns (one it added, or a legacy full copy, which the Knowledge page flags as overriding the catalog and an admin can turn back into the catalog file plus board rules). Hooks and `mcp.json` take no overlay. A catalog file with no board row is served as is; an overlay whose catalog file is gone is kept but not served. Slop hashes the catalog's agent set at start and bumps the agent-set version of every board that followed a different hash; approved learnings write only the overlay, and a learning that should change the generic text is a catalog candidate, i.e. a suggested change to `catalog/`.
- **Delivery:** `sstor init` fetches the board's agent set with `get_agent_set(board)` with sstor's own sign-in (the developer's OAuth login through sstor's Cognito app client), writes it into the checkout and records the version in `.claude/slop-agent-set.json`. The files are committed in the project repo, so every checkout, including a routine's cloud checkout, has the agents registered from the start. Updates ride along in the next glob commit.
- **Local-run spec:** what sstor builds and launches in a session's server window is one board knowledge row of its own kind (`local_run`, name `local-run`): JSON `{ "build"?: string, "launch": string }`, each one shell command line (no newlines or NUL, at most 2,000 characters), no other keys. sstor runs it on developers' machines, so it changes only through an approved KB item (a learning routed or retargeted to it is drafted as the whole value; the first value arrives the same way, and there is no import or upload of it), is checked on every write and every read (a stored value that fails the check isn't served, and the problem is reported), and is stored in canonical form (build first, two-space JSON) so its versions diff cleanly. It is not part of the agent set: changing it bumps no agent-set version, it is never overlaid or written under `.claude/`, and its effect checks go by time. `get_agent_set` and the download carry it beside the files (`localRun`, null when the board has none); `sstor init` writes it to the gitignored `.sstor/local-run.json`, removes that file when the board has none, and leaves it alone when slop sends no value (an older server) or reports the stored one invalid. The Knowledge page shows it read-only.
- **Routines** use the committed copy. At the start of an unattended run the orchestrator compares the committed version with `get_agent_set`; if slop's is newer it writes the new files and commits them with the glob, and they take effect from the next session (files written during a session only register in the next one). Routines need no session-start hook.
- **What goes in a definition and what goes in a document:** short rules that always apply to one agent go in that agent's definition, whether generic or project-specific (they are always present and carry system-prompt weight). Bulky or situational knowledge (conventions, architecture, testing guides) goes in documents, loaded by area and passed to agents by their audience.
- The knowledge base is searchable at runtime through MCP tools such as `get_conventions`, `search_text` and `search_semantic`, and agents submit learnings with `submit_learning`.
- **KB catalog:** generic, non-sensitive starter documents in slop's public repo under `catalog/kb/` (to start: TypeScript conventions, Python conventions, a generic review checklist and a build-doc template), each with the same frontmatter as any KB document (`area`, `audience`, `description`) plus a catalog ID and version. When a board is created, an admin picks the entries to import, with suggestions pre-ticked from the repo's languages (GitHub's languages API). Importing **forks** the entry: the board gets its own versioned copy, records its source (`catalog:typescript_conventions@3`) and can edit it freely. Forks don't sync: when a catalog entry's version moves past the one a board document was forked from (its source still `catalog:<id>@<v>`), the Knowledge page marks the document "Catalog has a newer version" and shows a read-only two-way line diff (board body against catalog body, frontmatter stripped), so an admin can copy changes across by hand; nothing is overwritten.
- **Other ways in:** a project's existing docs are uploaded on the board's KB page (files or a folder; frontmatter sets area and audience, otherwise Haiku suggests them and the admin confirms), or imported from a session with the admin-only `import_knowledge` MCP tool. Knowledge only the code holds is drafted by the `/kb-bootstrap` command, which runs in a checkout, reads the repo and submits the missing documents (build doc, conventions as practised, architecture overview) as new-document proposals. All three paths end as KB documents or proposals, so admin approval still governs what agents receive.
- **Script catalog:** slop keeps reusable scripts and config templates; boards select the ones they use, and builds and setup fetch them from slop's public endpoint. Claude Code generates the initial set during the build: a CodeBuild buildspec for PR checks that reads the glob labels; a buildspec that deploys a branch to the glob's environment; an ATF trigger buildspec; the sub gate GitHub Action; `.coderabbit.yaml` and `review-guide.md` templates; a PR-Agent configuration template; and the Google Meet Apps Script. The `sstor` changes are specified in the sessionator document.

**Self-improvement (KB items)**

Each proposal is an `s<board>k<n>` KB item linked to the globs that produced it, and nothing reaches the knowledge base or the agent set without human approval.

- **Provenance:** every run, artifact, failure report and learning records the board's agent-set version it ran with (from `.claude/slop-agent-set.json`), alongside the model. Slop can then compare signals before and after any change. Runs take their version from their commits: the catalog orchestrator and `/finalise` add a `Slop-Agent-Set: <version>` trailer to every commit, recorded on the push's `CommitPushed` event; a glob without one takes the highest version on its artifacts, failures or learnings, else its version is unknown (and it is left out of agent-file effect checks). An approved agent-file change records the board's agent-set version it created, which is where its effect check starts. A superseded run's `RunEnded` event records its cause (take-over, start again, pick-up, PR closed, deleted).
- **Capture (self-reports):** at the end of each run (orchestrator phase 6 for sames and subs, `/finalise` for supers, the end of each routine run) the orchestrator calls `submit_learning` once per learning with type (decision, gotcha, pattern, agent-behaviour), statement, evidence (glob, files, review findings or failures) and an optional suggested target. `agent-behaviour` learnings report something an instruction would have prevented: a review finding the implementer should never have produced, a test pass that failed because of how the code was written, and above all a developer correcting the agent in the session. Agents never edit the knowledge base or the agent set directly.
- **Signals slop mines (weekly job, marked as mined):** review findings are classified by Haiku as they arrive (e.g. "missing test for changed function", "unhandled error path") so they can be counted. Each local review (`put_artifact` with `local_review`) and each CodeRabbit inline comment is queued as a review source in the same transaction; nothing is parsed or asked in the request. A background job (the KB pipeline's claim, lease, deadline, retry and AI-unavailable rules, with a 90-second deadline per split call and a 30-second one per classification; a blank review has nothing to split and makes no call) splits each source into findings: a local review that uses the change_reviewer's IN-SCOPE and SUGGESTIONS sections is split by those sections' list items (with the round and the `[path:line]` they name; status tables and sections compiling earlier items are skipped), any other review by one Haiku call whose findings are kept only when their quote is found verbatim in the review, and a CodeRabbit comment is one finding (severity from its label, text up to its first details block). A finding repeated in a later version or round of the glob's reviews is stored once when its text is the same (exact-normalised-text dedupe, by a fingerprint of its text); Haiku splits of different versions paraphrase, so their findings mostly don't collapse. Each finding is then classified by one Haiku call into a fixed class list (missing-test, weak-test, unhandled-error, edge-case, concurrency, security, input-validation, timeout-resource, performance, logic-error, ui-state, migration-schema, spec-drift, convention, dead-code-comments, dependency, scope, or other with a note saying what the class would be); a finding still unclassified after three attempts shows as "couldn't classify" and counts toward nothing. The glob view lists the findings by class with their counts, severity, location, round, source and commit, as plain text.
  The mining job runs per board when 7 days have passed since its last run (checked hourly; a `board_jobs` lease keeps two servers from both running it, a run records its result only while it still holds the lease, and each run's transaction also takes the board job's lock, so a run that outlives its lease can't raise the same signal twice), and admins can Run now from the Knowledge page: it takes the lease and answers at once (already running when another run holds it), and the header shows the job running (polled slowly while it runs) and then the last run's figures. Code-host calls that read manifests time out after 30 seconds. Each run measures the last 28 days of the board's events, artifacts and findings (findings by when their review or comment was written, not when it was split); a signal over its threshold becomes an open `mined` KB item (submitted by `slop`, the board's current agent-set version) that the KB pipeline routes, deduplicates and drafts like a submitted one. Its statement comes from the signal's template, its evidence gives the window, figures (occurrences only when they differ from the affected count), threshold, affected globs and up to 5 quoted examples (a superseded run's cause, how long it had run and the last reason recorded; a failed commit's failing check when the build event names it, or a note that it wasn't compared with the base branch and may be inherited from a red base), its suggested target is the agent file (or document) named below, and it carries the signal (key, figures, up to 20 globs, examples), shown on the card as a figures table with a "Mined" badge. Signals, with their data and thresholds (`min` globs unless stated):
  - Recurring classes of local-review or CodeRabbit findings (`finding:<class>`; IN-SCOPE local findings and non-nitpick CodeRabbit ones, `other` left out; the statement names the sources that found them): the implementer isn't preventing them. At least 3 globs and 25% of reviewed globs.
  - Classes CodeRabbit finds on a commit whose local review missed them (`blind_spot:<class>`; compared with the local review of the same commit, short SHAs matching by prefix, else any of the glob's): a change_reviewer blind spot. At least 3 findings across 2 globs.
  - Many deviations from the plan in the implementation record (`plan_amended`; 3 or more lines under the latest record's `## Deviations`, for every glob type), or plan.md edited before a rerun (`plan_edited_rerun`; the summary, plan.md or an attachment changed between a failed or superseded run and the next queued one). plan.md v1, whether written at creation or backfilled from the summary (provenance `backfill`), is the baseline and never counts as an edit, so `plan_edited_rerun` counts fall for globs whose v1 was first written after a run ended. At least 3 globs and 25% of globs with a record; at least 2 globs.
  - Review cycles reaching the round cap (`review_cap`; supers left out, since a super keeps one review with rounds per strand; the local review's `reviewStats` when recorded, with a cap of at least 2, else 3 or more rounds named in the review's `##` headings), and tester FAIL→fix loops (`tester_loops`; from `reviewStats`): the implementer or tester. At least 3 globs and 30% of reviewed globs (of globs with review stats for loops).
  - Recurring `report_failure` reasons (`failure:<reason>`; run failures and interactive failures, the reason lower-cased without URLs, IDs, SHAs and numbers, first 80 characters), and routine runs ending in take-over or start-again (`run_superseded`; the recorded cause, or for older runs the events of the same transition): usually an orchestrator gap, especially in unattended mode. At least 3 failures with one reason; at least 3 runs and 20% of ended routine runs.
  - Frequent sub-to-same conversions (`sub_converted`; a failed sub gate), and CI failing after local checks passed (`ci_after_local`; distinct failed commits per glob that had a local review or a routine's push, leaving out failures marked as inherited from a red base branch): local checks or scope control not matching the project. At least 3 and 30% of gated subs; at least 2 globs and 10% of globs with builds.
  - New libraries or frameworks with no conventions yet (`dependency:<name>`; dependencies a merged glob's commit added to a `package.json`, `pyproject.toml`, `requirements*.txt`, `go.mod` or `Cargo.toml`, read from the code host, that no board document mentions): a missing document. All found in one run are raised as one item, and each name only once.

  A `kb_signals` row per board and signal key keeps a signal from being raised every week. While its item (or the open item it was merged into) is open, each run refreshes the item's figures and adds a "Week of <date>: affected/eligible" line to its evidence ("Mined by slop, week of …" on a submitted item), without drafting it again; a second run on the same day with the same figures adds nothing. Once approved or covered it is never raised again (the effect check watches it). Once rejected or suppressed it stays quiet for 12 weeks, and is raised again after that only at 1.5× the signal's own rate at the time (dedupe may still suppress it). A chain of merged or covered items longer than 10 links counts as no item, so the signal is raised again. A signal below its threshold, or not measured, counts the runs in a row it has been below (an unmeasured one keeps its last figures and measurement time).
- **Processing (a slop background job, a plain loop over `kb_proposals` like the outbox):** `submit_learning` returns the item's ID at once; the job then claims each item due for routing or drafting (a conditional write that holds it for a lease, so two workers can't both take it) and processes it: first routing and dedupe, then, as a separate step, its draft.
  1. *After submission (Opus, two calls):* route the item (step 2), then deduplicate it by LLM comparison (no embeddings yet) against open items, approved items (statement and target), rejected items (statement and reason) and the current text of the routed target's section (the whole target if it has no section, truncated when long); each list is capped at the newest 100. The dedupe prompt doesn't lead: the model first restates the learning's specific fact in one sentence, then classes each of the few closest candidates (at most 5) as *same fact*, *related topic only*, *unrelated* or *contradicts*; only *same fact* may close or flag the item as a repeat or as covered, and only *contradicts* may flag a contradiction. The default answer is new: overlapping topic, tool or area is not coverage, and when unsure it answers new, since an admin reviews every open item. The restated fact and the classifications aren't stored, but every claim needs them: a claim on a candidate the model classed otherwise, or didn't class at all, is dropped (relations are compared ignoring case, `_` and `-`). Outcomes, written in one transaction with conditional writes: a near-duplicate of an open item is closed as **merged** into it, which gains the evidence, its globs and its occurrence count; a match to a rejected item is closed as **suppressed** (re-read in the same transaction: it must still be rejected, and not kept apart from the item, as a merge's or coverage's item must still be open or approved and not kept apart; it is written back unchanged on the version read, so a change committed meanwhile rolls the outcome back to be retried); something an approved item already says is closed as **covered**, and that item gains the evidence and count (evidence fields only, never its decision); coverage by the target's text only flags: the item stays open (and is drafted as usual) with "May already be covered by <target › section>", the quoted sentence and the model's one-line reason, and the admin approves, rejects or keeps it; every claim must quote the text the model was shown (an item's statement, or the target's text), checked mechanically (whitespace, case, and sentence punctuation or quote marks at either end ignored; the quote is kept without those ends, and they never count towards its length), and a claim whose quote isn't found is dropped, leaving the item open; a merge or suppression claim needs two quotes, one from the open or rejected item's statement and one from the new item's own, each found in its own statement (a quote found only in the other statement is dropped), and the closed item keeps both quotes (`by: intake`), which its card shows ("Merged on intake into <ID>" or "Suppressed: matches rejected <ID>", then "“…” states the same fact as “…”"); every closing claim (merge, suppression, or coverage by an approved item) also needs each quote it rests on to be at least 4 words and 20 characters (whitespace collapsed, as consolidation's), else the item stays open, flagged with the other item's quote and a note that it was too short to close the item on: "May already be covered by approved item <ID>", "May repeat open item <ID>" or "May match rejected item <ID>" (the last two with the item's own quote too), naming which quote was too short, and only one such flag at a time (suppression's, then merge's, then coverage's, then the target's), though a target flag hidden this way is shown beside it ("The current text may say it too", with its quote and reason); a flag never names an item an admin kept apart from the item (a target flag it hid is shown instead); when a merge closes the item, its flag for a rejected item moves to the open item it merged into, unless that has a flag already or is kept apart from the rejected item, naming the merged item its own quote is from ("merged-in <ID>"); a target with no text yet (a new document, an empty overlay) can't cover or contradict anything; a contradiction with the target's text or an open or approved item keeps the item open with the contradiction flagged. Merged, suppressed and covered items leave the open queue, keep their links and can't be decided; an admin can reopen one that has a target (back to the open queue with it, drafted again but not routed or deduplicated again; the item it was closed against keeps any evidence it gained). Each LLM call has a deadline (2 minutes, below the 5-minute claim lease) so a stalled call can't hold the pipeline; unusable answers, LLM errors and timeouts get up to three attempts in all, with backoff between them (the same for drafting); the item is then marked routing-failed, stays open and can still be decided by hand, or an admin retries it (back to routing without a target, to drafting with one). An *LLM unavailable* failure (expired AWS sign-in, no credentials, no model access) is not an attempt: the item keeps its stage and attempt count, is released to be tried again a minute later, and its card says "Waiting: AI unavailable — <reason>" (no Retry; it resumes by itself), so a credential lapse never fails items. A *Bedrock busy* answer (ThrottlingException, ServiceUnavailableException ("Bedrock is unable to process your request"), ModelNotReadyException, ServiceQuotaExceededException, InternalServerException, SDK timeouts) waits the same way without an attempt, but with exponential backoff and up to 25% jitter (1, 2, 4, 8, then 15 minutes, counted in memory per item, so a restart starts over at a minute) and says "Waiting: Bedrock busy (retrying at HH:MM UTC)"; findings, review splits and search jobs wait the same way, and only real failures (unusable answers) spend attempts. On start, open items that had gone `failed` with a busy message are put back at their stage (`routed` when they had a target, else `pending`) with fresh attempts. While either KB model is down (health is tracked per model, so intake's model doesn't count) the job claims no items except one probe a minute, whose call tells it when the LLM works again; a claim that finds nothing due isn't a probe, so the first item due is probed on the next poll. A credential or access failure that surfaces only when a call's deadline fires still waits rather than counting as an attempt. Document proposals (`/kb-bootstrap`) skip routing and drafting: their target is the proposed document, and the proposal is its own draft.
  2. *Routing:* a project fact goes to a document for the relevant audience (e.g. "generated files live in `src/gen/`"), unless it is a short rule that always applies to one agent, which goes in that agent's definition (e.g. "never edit `src/gen/`"). Process behaviour goes to the agent's definition (e.g. "write the regression test before the fix"). The target is a document or agent file and the heading it belongs under; an agent-file target always means the board's overlay (its `## Board rules`, or the whole file for one the board owns), so the section is a heading there or none to append. When no document fits, the target is a new document with a suggested name, area, audience and description. The submitter's suggested target is a hint. Anything that would hold for any project is also flagged as a catalog candidate with a one-line reason, shown to admins as a suggested PR to slop's `catalog/`.
  3. *Drafting (Opus, one call per routed open item):* every routed item is drafted, not only recurring ones. Opus gets the statement, type, evidence (including near-duplicates'), source globs, the target and the target's full current text: a document's body; for an agent file the board's overlay, with the catalog text as read-only context (only the overlay can change); for a new document its proposed name, area, audience and description and the board's document index, to avoid overlap. It answers with one section's full new text (the existing heading it replaces, which may be a better heading in the same target than routing chose, or none to add a new section), or a new document's whole body, plus a one-line rationale. Slop splices the section into the target (up to the next heading of the same or a higher level) and shows the diff of the whole text, and records the target version the draft was made against. Failures retry with backoff like routing, then mark the item drafting-failed (still decidable). A draft whose target has since changed (another approval or edit) goes back to be drafted again: every write to a document or agent-set file re-queues the open drafts against it in the same transaction, a target that changes during the Opus call releases the item, and approving a stale draft is refused and re-queues it.
  4. *Weekly consolidation (Opus, the routing model):* a `board_jobs` job, `consolidation`, run per board when 7 days have passed since its last run (checked hourly, after mining when both are due so the stale rule reads that week's below-threshold counts; items mining raises are still pending, so they are compared once drafted, the next week; under a lease and lease-conditional result like mining's, its lease covering the worst case: 21 calls to the LLM deadline, 15 minutes for the writes, and a mining run's 30-minute lease, since its merges and stale pass wait on mining's board lock), with Run now on the Knowledge page beside mining's status. It merges open items that state the same fact under intake dedupe's safeguard, and flags stale ones; a model never closes an item on its own say-so.
     - *Candidates:* open statements the pipeline has settled (drafted, or failed), not document proposals, newest 200. Items still being routed or drafted are the pipeline's.
     - *Candidate pairs:* one call gets each candidate's ID, type, target, evidence count and statement (one JSON object per line, so a statement can't run into the next), and proposes at most 20 pairs that may state the same fact (none when unsure). Proposing closes nothing. Pairs an admin kept apart are dropped. Pairs remembered as not the same fact (Memory) are listed after the candidates as already checked; any proposed anyway are counted and dropped before the cap of 20, so they don't crowd out new ones.
     - *Verification:* one call per pair restates A's fact and classes B as same fact, related topic only, unrelated or contradicts; for same fact it quotes each statement. A pair merges only as same fact with both quotes found verbatim (ignoring case and whitespace) in their statements, each at least 4 words and 20 characters (whitespace collapsed); anything else, an unusable answer or a failed call leaves both open.
     - *Memory:* the job remembers (`board_jobs.state`) the pairs it verified as not the same fact, by each item's ID and a hash of what the calls read of it (statement, type and target), and doesn't verify them again until either item's statement, type or target changes (an admin's edit or target change); new evidence, mining's weekly refresh, a stale flag or a merge into the item keep it. It keeps the newest 500 such pairs. When a run leaves no pair unanswered (every pair merged, found different, or refused by the rules; a pair whose item an earlier pair merged away is verified against the survivor in the same run, unless that pair was already asked), and the candidates it leaves are the ones it compared (none added, none gone but its merges, none's statement, type or target changed; another writer meanwhile, such as an item drafted or edited, means they aren't), it also remembers the candidates as it left them, by the same hash; the next run makes no candidate-pair call while they are unchanged.
     - *Merge:* the survivor is a drafted item before one the pipeline gave up on, then the more repeated item, then the older. It keeps its draft and target and gains the other's evidence, globs and count (as an intake merge), and its signal when it has none; the board's `kb_signals` rows for the closed item point at the survivor. The other is closed as merged into it, with both quotes (its card says "Merged by weekly consolidation" with them), and any stale flag on it cleared. Both writes are conditional on the versions verified, in one transaction that also takes mining's board lock; a pair whose item changed meanwhile is skipped.
     - *Keep apart:* reopening a merged item records the pair on both items in the same transaction, so consolidation never merges them again. A merge carries both items' kept-apart sets onto the survivor, and a pair is refused when either side holds the evidence of an item kept apart from the other, so no chain of model-verified merges (in one run or across runs, by consolidation or intake dedupe) joins what an admin split.
     - *Stale (a documented rule, no model):* a settled open item is flagged stale when it has no evidence newer than 60 days (its submission, evidence merged into it, its signal's last measurement), or when it is mined and its signal has been below its threshold for 4 runs in a row. The flag only shows on the card with Not stale (admins) beside Reject; nothing is closed. New evidence clears it, and Not stale clears it and suppresses it for 60 days.
     - *Order:* the open queue is ordered by evidence count (occurrences, or source globs if more), then the freshest evidence; cards show "evidence from N globs".
     - While the routing model is down the job is skipped without calls (the last run stands) and the next hourly check tries again, even after a Run now within the week; a run that finds it down mid-way keeps the merges it made. A failed run (of either job) keeps the last run too, and is tried again after 1 hour, then 2, 4 and so on, doubling with each failure in a row up to 24 hours; a skip in between keeps the count, so a model that alternates between down and failing still backs off. Each run records the candidates, pairs proposed and verified, merges, pairs skipped, pairs already checked, whether the candidates were unchanged, and items flagged stale or cleared; the Knowledge page shows an unchanged run as such, and a failed run with when it tries again.
- **Merge policy:** which paths clash between globs is one board knowledge row of its own kind (`merge_policy`, name `merge-policy`), built like the local-run spec: JSON `{ "exclusivePaths"?: string[], "sizeIgnoredPaths"?: string[] }`, validated by hand in core on every write and read (an object with no other keys; each list at most 50 path globs relative to the repo root, each non-empty, one line, at most 200 characters, no leading `/` and no `..`, repeats dropped; `{}` is valid: the policy exists and nothing is configured), stored in canonical form. It changes only through an approved KB item (a learning about which paths clash, or which are left out when a sub is sized, is routed or retargeted to it and drafted as the whole value; the first value arrives the same way; there is no import, upload or edit door), and an agent may not approve it (a person decides which globs hold for each other). It is not part of the agent set: no agent-set version bump, not in the bundle, effect checks go by time. A stored value that fails the check is never served or acted on (the Knowledge page shows the problem and the policy acts as empty). The Knowledge page shows it read-only. `exclusivePaths` are path globs that only one open glob may change at a time (for slop, `apps/server/drizzle/**`, since migration numbers and the journal clash). `sizeIgnoredPaths` are left out when a sub's size is measured: defined here and validated only; the sub gate reads it in a later change. The board's `sensitivePaths` stay a board setting for now; moving them into the merge policy is a later change.
- **Exclusive paths (holds):** when a glob is about to start a routine run (created as a sub or with `autoTrigger`, changed to a sub, Start on a same, or released: row 33), slop checks whether another open glob (one with a branch, not merged) may change an exclusive path: its branch already does (the code host's compare against the base, read through the `BranchFiles` port and cached for a minute per branch head; GitHub lists at most 300 files; a branch that can't be read counts as unknown and never holds), or it is in Doing with no file there yet and a plan that names one. It can't know beforehand whether the new glob will touch those paths, so it applies the hold only when the new glob's plan.md names an exclusive path (the literal directory of an exclusive glob) or a migration (the words "migration", "schema", "drizzle"), or intake's file guess includes one; otherwise the glob starts and is warned (row 35) once its branch touches an exclusive path another open glob also changes. A hit becomes an implied `after` (`impliedAfter`: `{ id, paths }`, shown as "waits for s15b18: both may change apps/server/drizzle/**"), released like any other (row 33); a hit that would make a cycle is skipped, and a hold a person overrode (Start anyway) is not added again. Intake returns the file guess (`files`) and `suggestedAfter` (unmerged globs the request says to wait for after "after", "once", "until" or "wait for"); both are advisory.
- **Review:** the KB view shows each open proposal (most evidence first, then the freshest evidence) with its target as a path, the diff (computed against the target's current text, with context; long diffs collapsed), rationale, evidence with links to the source globs (`/boards/{b}?glob=<id>` opens a glob's view, or the signed-off page's), occurrence count and the number of globs its evidence comes from, flags (stale, with Not stale; catalog candidate with its reason, possibly covered by the target's text, or by an approved item on a quote too short to close it, with the quote, contradictions with links, stale draft) and processing state (routing, drafting, the last error and next try while retrying, waiting for the AI with its reason and no Retry, failed with Retry); members see it read-only. Merged, suppressed and covered items (with Reopen for admins), and approved and rejected ones with their outcome or reason, are listed collapsed: the newest 50 of each group (decided items by when they were decided) with their totals, and older ones on request, up to 1,000. A draft section is never a document's level-1 title when it has lower-level headings (that would replace the whole document); such a draft is appended instead. For now only board admins approve (one click applies the draft: the section is spliced into the current text, documents keep their frontmatter, a new document gets its proposed one, agent files write only the overlay), edit then approve, change the target (the draft is cleared and redone against it, without routing again), keep the statement as an approved learning (served by `get_conventions`), or reject with a reason (this may be opened up later). An admin's agent can also clear the queue through MCP (`list_kb_items`, `decide_kb_item`): the same service calls as the buttons (version, drafted-against version, validation, history, agent-set version bump and effect-check baseline), recorded as the signed-in admin with `via: 'agent'` inside the item's `outcome` (a rejection by an agent records `outcome: { kind: 'rejected', via: 'agent' }`; no column of its own), and the Knowledge page shows "via agent" beside the decider. An agent approves the item's draft as drafted, or with `editedDraft`, which goes through the page's edit-then-approve path (validation, drafted-against version check, splice, history, agent-set version bump). Approving is always refused (use the Knowledge page) for the local-run spec, the merge policy (slop executes or enforces them) and whole-document proposals. Agent-set targets (agent, command, hook, settings, mcp, claude_md) and items with contradicts flags are refused too unless the board's `agentKbApproval` setting is `docs_and_agent_files` (default `docs`; an admin sets it in board settings under Knowledge, "Agents may approve agent-file and contradicting items"; stored as the `boards.agent_kb_approval` column); a contradicting item then needs a `reason` (why the contradiction is intended or resolved), recorded as the decision's reason. Rejecting any item is allowed. The Knowledge page's "Decided by agent (last 7 days)" filter lists the agent's decisions, and an admin can Reopen any of them: an approval's change is reverted through a new knowledge version (refused when the target changed since, or the approval created the document) and the item returns to the open queue to be drafted again. Approval creates a new document version in Postgres (and a new agent-set version for agent items), picked up by the next `sstor init` or routine run. Rejections are kept to suppress repeats.
- **Effect check:** after an approved change, slop watches the signal that triggered it (e.g. the rate of "missing test" findings per glob) over the following globs that ran with the change. If it hasn't dropped after a per-board number of globs, or another signal got markedly worse, slop raises a proposal to revise or revert the change, with the before and after figures. Humans still decide.
  - *Which items:* approved items with a signal: mined items, and a submitted item when the admin picks one of the board's signals as measured now ("Watch signal" when approving; none by default). A watch signal is refused for an item that already has a signal (its check watches that one) and for a document proposal. `dependency:` signals aren't measured by effect checks (the check reads no manifests, and documenting the dependency is the fix), so they aren't offered under Watch signal and approving a dependency item starts no check. Approving sets the check watching, and the approval checks that item on its own at once in the background so the before figures show straight away (not a run of the job, so the board's daily schedule stands); a failure there is logged and never fails the approval. A signal picked this way belongs to the approved item in `kb_signals` (unless an open item already holds it), claimed under mining's board lock, so mining doesn't raise it again while the check owns it. Approving a revise-or-revert item watches the signal its original watched; so does approving the open item a revise-or-revert item was merged into by consolidation, when it had no signal of its own and took the `effect:` signal over.
  - *Attribution:* an agent-file change is measured by agent-set version: its outcome records the first agent-set version with the change (the board's version after the approval), and a glob counts after the change when its version is at least that one. An approval that left the file as it was bumps no version, so it is measured by time (the content was already being served). A glob's version is its commits' `Slop-Agent-Set` trailer, else the highest version on its artifacts, failures or learnings; globs with no known version are left out. Documents and approved learnings are served at runtime without a version, so they are measured by time: a glob counts when its first recorded work (its first artifact, run trigger or pick-up) came after the approval. An approval recorded before agent-set versions were kept in outcomes is measured by time too.
  - *Windows:* N globs a side, from the board setting `effect_check_globs` (default 10; admins set 3 to 50 in board settings; a watching check follows the setting, a final one keeps the N it was decided on). Only merged globs count, so the card's figures can differ from the mined item's, which count every eligible glob in mining's 4-week window. Before: the last N globs first merged before the approval that are eligible for the signal (the signal's own per-glob rule, e.g. globs with builds for "CI failing after local checks passed"); a glob that merges again later (Merge and continue) stays on this side, and this side counts only activity up to the approval, so work done with the change never moves the before figures. After: the first N eligible globs, by first merge, that first merged after the approval and ran with the change. Each side's rate is its affected globs over its globs. Every run reads the activity from a year before the approval.
  - *Verdict*, once the after side has N globs: *improved* when the rate after is at most 70% of the rate before (so also when it fell to none), otherwise *not improved*; *worse elsewhere* when it improved but another signal is markedly worse over the same globs: at least 3 globs eligible for that signal on each side, its rate after at least twice its rate before and at least 20 points higher. *Unmeasurable* when no glob before the approval is eligible. The comparisons are exact (whole numbers), so a boundary isn't lost to rounding.
  - *Raised item:* for not improved or worse elsewhere, a mined KB item of the original's type. Not improved: "Revise or revert s15kN (<statement, cut>): after N globs with <agent set vN or later | work started after <date>> the rate of <label> is X% (a/b), against Y% (c/d) before." (naming the worst other signal that rose too, if any). Worse elsewhere leads with the gain to keep, then the side effect over that signal's own globs: "Revise s15kN (<statement, cut>): after N globs with <basis> the rate of <label> fell from Y% (c/d) to X% (a/b), but the rate of <other label> rose from … to …." Its evidence gives both sides with their globs; its suggested target is the original's target, its signal key `effect:<item>`. It goes through the KB pipeline like any mined item, except that dedupe never sees the original or another item raised for it, so it can't be closed as covered by the change it questions. The check records it and is final; the card's link follows the item to the one it was merged into.
  - *Schedule:* a daily `board_jobs` job, `effect_check` (checked hourly with the other jobs, under its lease), with Run now and its last run on the Knowledge page. Each item's check runs in its own transaction under the board's effect-check lock and re-reads the item, and its write is conditional on the item's version, so two runs never raise twice. No LLM calls.
  - *Shown on the approved card:* "Effect check: watching (3/10 globs since v12)" (or since the approval date) or the verdict, with the basis and when it was last checked, a before/after table (affected, of, rate, the affected globs as links; the after row is "so far" while watching; rows for any signal that got worse), and a link to the raised item.
- **Data:** a `kb_proposals` table (ID, status (open, approved, rejected, merged, suppressed, covered), type, statement, processing state, target (kind, name, section, or a proposed new document), drafted section and the target version it was drafted against, rationale, evidence and evidence added by near-duplicates, occurrence count, duplicate, suppression, coverage, possible-coverage and contradiction links, source submitted or mined, the triggering signal for mined items (key, kind, agent, label, window, figures, globs, examples), catalog candidate and reason, decision and reason, the stale flag with its reason and when an admin last kept the item, the items an admin kept apart from it, the quotes a consolidation merge or an intake merge or suppression closed it on, and an approved item's effect check (`effect_check`: state, the signal key and label watched, basis, N, before and after figures with their globs, signals that got worse, the raised item, when last checked); later an embedding) alongside versioned knowledge documents and agent items; a `review_sources` table (the queued local review artifact or CodeRabbit comment with its text, commit, agent-set version, location and split state); and a `review_findings` table of classified findings per glob and commit (source, commit, agent-set version, severity (in scope, suggestion, unknown), round, path and line, text, fingerprint, class and the classifier's note, classification state). A glob's sources and findings are deleted with it. `kb_signals` holds one row per board and signal key (the item it last raised, its last figures and measurement, when it was raised, and the runs in a row below its threshold); `board_jobs` holds each board job's last run, its result, the lease of the server running it, and what the job keeps between runs (`state`: consolidation's checked pairs and candidates, and the sub limit's remembered bug references and failed asks). `boards.effect_check_globs` holds the effect check's N; `boards.sub_max_changed_lines` holds the learned sub size limit and `sub_limit_changes` its history (Sub review); an approved agent-file outcome records the board's agent-set version after it (`agentSetVersion`).
- **Cost:** the KB pipeline is the most important part of the system, so it uses Opus 5.5 (Bedrock's US cross-region inference profile, with default sampling): two calls per submission (routing, dedupe) plus one draft per routed item (and per re-draft when its target changes), cents per learning. Weekly consolidation costs at most one Opus call over up to 200 statements plus up to 20 verification calls per board per week, and none while the candidates are unchanged; pairs already found different aren't verified again, and failed runs back off to one try a day. Review findings cost one Haiku split call per free-form local review, then one Haiku classification call each. The learned sub limit costs one Haiku call per new bug report that names a recently merged sub (remembered unless it blames it, at most 3 tries without a usable answer), and none while the model is down.

Approved changes are served on the next fetch; no PR is needed.

## Review, merge and GitHub

From now on the team works with a branch and PR per glob, replacing direct commits to master. Slop links everything in GitHub to globs by one convention: the branch name is the glob ID, and slop creates that branch itself.

**Sub review** runs as a GitHub Action and reports back to slop. It starts with basic checks (lint, type check, tests). Each board has a sensitive-paths setting, empty for now. A sub whose diff (against the base branch) exceeds the board's sub size limit also converts. **How the size is measured:** the changed lines of every file except generated ones. The left-out paths are the board's merge policy `sizeIgnoredPaths` (knowledge, changed through approved learnings; there is no board setting); with no merge policy, or an empty list, the built-in defaults apply: lockfiles (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`) and `**/drizzle/meta/**`. The sensitive-path check still sees every file. The gate's reason says what was left out ("Changes 701 lines, not counting 3,047 generated (limit 1750)"), and the verdict records the counted lines (`changedLines`) and the left-out ones (`ignoredLines`). The learned limit's line counts read from a merge commit leave the same paths out. A flagged sub converts to a same. The gate's verdict (`SubReviewCompleted`) records why it converted (`cause`: size or sensitive), the lines the sub changes and the limit applied; verdicts recorded before these fields are read from their reason ("Changes N lines (limit L)").

The **sub size limit is learned from outcomes**, not set by admins (there is no manual override; the history makes every move auditable). It starts at 2,000 changed lines and stays between 200 and 5,000, moving by a fixed step of 250 lines either way. An hourly `board_jobs` job, `sub_limit` (under its lease, with Run now in board settings), reads the subs merged up to 28 days before its last successful run (the 14-day outcome window plus a 14-day margin; a failed run doesn't move that point), so an outcome in a window's last hour, or a candidate that was waiting when its window ended, is still decided on a later run, and records each sub's outcome once:

- *Merged unchanged (raises it):* the sub converted for its size, then merged with no commit after the conversion (pushes from superseded runs don't count) and no sign-off label moved to `added`. It is decided once the glob is signed off, or 14 days after the merge. The limit becomes `min(5000, L + 250)`, for limit L.
- *Needed fixes after merging (lowers it):* the sub passed the gate and merged, and within 14 days of the merge either a sign-off label (FR, CR or QA) moved to `added`, or a bug glob created after the merge names the sub's ID in its title or summary and the findings model (Haiku, one call with a 30-second deadline) answers that the bug report says the defect was introduced by that sub, with a quote slop finds verbatim in the report and at least 4 words / 20 characters long. Naming a sub isn't blaming it, so a bug that only mentions it changes nothing. The limit becomes `max(200, L − 250)`. A label outcome is used without asking the model. A passed sub whose verdict has no line count is measured from its merge commit (the code host's diff of the commit against its first parent, which for a squash merge is the whole PR; at most 300 files are counted); when that can't be read the outcome is recorded without a line count, since the count is evidence only. While the model is unavailable (or known to be down) bug references wait for the next run without calls. Answers that don't blame the sub are remembered by the bug report's text, so the same report isn't asked about again unless it is edited; a reference that gets no usable answer (unusable JSON or a timeout) 3 times is skipped and remembered too, and the run's result counts it.

Each outcome is recorded in `sub_limit_changes` (when, the limit before and after, the outcome, the sub, its changed lines (or unknown) and the evidence: the conversion and merge, the label's checklist item, or the bug's ID and verified quote), once per sub and outcome; an outcome the rule doesn't move (the limit already at a bound, recorded with the limit after equal to the limit before) is still recorded, so it isn't checked again. The board write is conditional on the limit the job read, in the same transaction as the history row, under the board's sub-limit lock; settings saves don't write the limit. Outcomes found in one run apply in order, each to the limit the one before left. The gate reads the board's limit when it decides, so a decision uses the limit of that moment, and a later move doesn't change it. Board settings show the limit ("Sub size limit: N changed lines (learned from outcomes)", read-only) with its history: date, from → to, why, the glob and the evidence, as plain text. The sub's changed lines are recorded as evidence but don't size the step. **When the limit moves:** a raise always applies, but a sub that needed fixes lowers the limit only when it was near it: its changed lines were at least half the current limit (`SUB_LIMIT_NEAR_SHARE`, beside the step). A smaller sub, or one whose size is unknown, says nothing about the limit (a 2-line sub needing a fix is not a size problem): its outcome is recorded with the limit after equal to the limit before, and evidence saying it was too small to say anything about the limit. Scaling the step by the project's age and size is a possible future refinement.

**Webhooks are best effort; reconciliation is the source of truth.** GitHub doesn't retry a failed delivery, so a restart or a tunnel blip can lose a push, check, ready or merge event and leave a glob waiting for nothing. The `reconcile` job (`SLOP_JOBS`; session servers don't run it by default) re-reads open PRs from the code host. On start it queues a `reconcile_pr` outbox effect (generation-checked, idempotent) for every glob with an open PR (in Doing, Implementing, In review or Merging); every 10 minutes it queues one, at most 25 per tick, for each glob that looks stuck: a ready PR with no check result for its current head that hasn't changed for over 10 minutes, or a glob a run is watching that hasn't changed for over an hour (`updatedAt` stands in for the last webhook, since every webhook that matters changes the glob). The executor reads the PR (open, draft or ready; merged with its merge sha; closed; head sha) and applies what was missed through the transitions the webhooks use: `merged`, `prClosed`, `commitPushed`, `prReadyForReview`, and `checksChanged` (which queues `refresh_checks`) when the head has no result. Each catch-up is logged (`reconcile: s15f9 head moved to … (missed webhook)`); it raises no notification beyond what the transition itself raises. A second run with nothing missed changes nothing.

**Merging**

- Squash merge only. The commit message starts with the glob ID, e.g. `s1t4: Fix login timeout`; PR titles use the same format.
- Repository rules enforce the merge guarantees for every entry point (GitHub UI, gh, sstor, slop): required checks must pass on the PR's current head commit and the branch must be up to date with master, so a stale passing result can never merge newer changes. For merges slop starts (subs and the Merge button), slop updates the branch, waits for the checks and squash-merges; a conflict (found when updating the branch, or reported by GitHub before it) leaves the glob failed in Doing with the reason "Merge conflict with `<base>`", never as failing checks. Resolve conflict on such a glob (row 20a), or on one flagged as below, posts one PR comment that mentions `@claude` (needs both the Claude GitHub App and a workflow that runs `anthropics/claude-code-action`, both board readiness items; it works in GitHub Actions with no local pull) and starts no routine run. The comment gives the glob's and the merged glob's ID, title and summary, the conflicting files, and the instructions: merge `origin/<base>` into the branch, resolve keeping both intents, run lint, type check and tests, push. It carries a marker with the request time, so a retried effect never comments twice. Merges done anywhere else are observed through the merged event.
- **Conflicts flagged after each merge:** when a merge to the base branch is observed (row 15, or Merge and continue), slop rechecks the board's other open PRs (`pr_open`, or `in_progress` with a draft PR) through the outbox: a `check_conflict` effect per glob that retries while GitHub has not computed mergeability. A glob that now conflicts records `conflict` (base, files, the glob that merged, time) and its card shows "Conflicts with `<base>` since `<id>` merged: `<files>`" next to the other stuck hints; the glob does not fail. A push to a glob with a flagged conflict rechecks it, and the flag clears once the PR can merge again. For a human implementer the card and Resolve conflict show `sstor --glob <id> --resolve` (and the git commands) and slop posts no comment. When the comment was posted and the PR still conflicts 15 minutes later, the card adds "Resolve locally: `sstor --glob <id> --resolve`".
- Every PR (sub, same or super) runs the repo's `checks` workflow (install, lint, type check, tests) on its head, including the head after slop updates the branch; the `checks` check and `sub-gate` are required on master (board readiness, `setup-repo.sh --protect checks sub-gate`). Slop's merge waits on GitHub's merge state, so a same or super whose head hasn't passed `checks` stays pending, and a failing one fails, as for subs.
- **Check states:** a head's check runs are *passed*, *pending* or *failed*. A **cancelled** run is none of the failures: it has no verdict, so it leaves the head pending (and the `sub-gate` lookup ignores it) while a newer run on the same head replaces it, as when a push or the `slop:sub` label supersedes a gate run in progress. If no newer run has come after 5 minutes, slop asks the GitHub App to re-request the cancelled run (best effort; only the app that created a run can) and keeps waiting. A cancelled run is never counted as a failed check. The repo's `sub-gate` workflow re-runs on a `labeled` event only for the `slop:sub` label, and other labels use their own concurrency group, so adding a label never cancels a gate run in progress.
- **Failed checks are explained:** when slop records failed head checks (`checksCompleted`, from a check event or a merge's update), it reads the commit's check runs through the `CodeHost` port and stores a short failure on the head checks: the first failing check's name, its failed step (the Actions job's steps), the first error lines from the last ~60 lines of the job log (a check run's ID is its job's ID for Actions) and the run's link. Lines are the log's error lines, not a summary; where the log can't be read, the run's own output is used, else only the check's name. The card shows "checks failed" with the step and first error on hover, the glob view's disabled Merge says the same, and a merge that failed on checks after updating the branch carries it in its reason. This is the first piece of the build-failure summaries (slice 7); an LLM summary of a long tail comes later through the LLM port.
- **A red base branch:** slop keeps the latest check result for the head of the board's base branch (`baseChecks`: head SHA, passed or failed, the failing check as above, the glob whose merge turned it red and when). A check finishing on the base branch (`check_run` or `check_suite` webhooks for it) queues one idempotent `refresh_base_checks` effect per board, which reads the branch head's checks and the head commit's subject (`<id>: <title>`, which names the glob that merged). A glob whose head fails the same check with the same first error as a red base is marked `inheritedFrom` the base (in either order: the mark is also set on the globs already failed when the base turns red, and cleared when the base no longer fails like that). Its card says "`<base>` is red (since `<id>`): not this glob's change", `get_glob` returns `failedChecks` with the same text and `headChecks.inheritedFrom`, and the board shows a banner naming the glob whose merge turned the base red while it is red. A failure inherited from the base is not "stuck": the routine isn't told its run hasn't reacted. The catalog orchestrator, in unattended mode, doesn't fix an inherited failure in the glob's branch: it waits and records it in the run's notes.
- **Re-run when the base is fixed:** when the base branch's head goes from red to green, slop queues an `update_branch` effect for every open glob (`pr_open`, or `in_progress` with a PR) whose failed head checks are inherited, generation-checked and idempotent (dropped when the glob has been pushed to since or no longer has an inherited failure). It updates the PR branch with the base through GitHub's update-branch call (the one a merge uses); the push resets the head checks and they run again on the fixed base. A conflict found by the update is flagged on the glob like any other conflict; a branch that is already up to date just loses the stale mark.
- Branch protection requires passing checks but no approvals; direct pushes to master are not allowed. For sames and supers, merging is the approval: the developer reviews the results on the glob and clicks Merge (on the glob or in GitHub). Slop merges subs once the sub gate passes.
- GitHub's "automatically delete head branches" setting is on. No other git cleanup for now.

**GitHub App**

- Slop reaches the repository through a `CodeHost` port (provision, labels, close, reopen, delete branch, merge state, squash merge); the GitHub App is its only adapter, and a host-specific webhook adapter turns deliveries into the same state-machine events. Another host (GitLab, Forgejo) would mean a new adapter pair, but routines and Claude's auto-fix only work with GitHub today, so that is the real lock-in.

- Slop's GitHub operations (branches, PRs, merges, check results) use the app's installation tokens, acting as `slop[bot]`. The private key lives in Secrets Manager.
- The app is allowed by branch protection to merge subs to master once required checks pass.
- One board maps to one repo.

**Webhooks:** the app subscribes to `push`, `pull_request`, `pull_request_review`, `pull_request_review_comment`, `issue_comment`, `check_run` and `check_suite`. A webhook adapter verifies the signature, reads the glob ID from the branch and calls the core, which records commits, PR ready and closed, merges, check results and review comments, and starts the glob's deploy when a push arrives and an environment is set. The glob stores references only. No reconciliation job; missed deliveries are redelivered by hand from the app settings.

**Review and CI results** attach to the glob through the branch name, with or without a PR. The sub review and other Actions report as GitHub check runs; slop receives them through the GitHub App's existing check webhooks and reads summaries and annotations from the Checks API. No slop credential is stored in the repo, and a crashed Action still arrives as a failed check. A REST callback remains for results that are not GitHub checks. The MCP and REST endpoints are separate driving adapters on the same application services.

## Environments and deployment

Each environment is represented by the commit it runs, and a glob counts as deployed there if its squash commit is an ancestor of that commit.

- **Environment roles** (board settings): *branch-deploy* environments receive glob branches (`allowBranchDeploy`); the *integration* environment is deployed by the base branch's own pipeline; *release* environments run release branches cut from the base branch, and one of them may be marked *production*. A board can have any mix, including none.
- **Release branches:** release environments run release branches cut from master. The ancestry check covers everything up to the cut point and ignores unrelated commits, so commits without globs never break tracking. Rollbacks resolve the same way.
- **On each deploy event,** slop rechecks all recent globs, including those previously marked deployed so rollbacks are handled, using GitHub's compare API, and stores the result on each glob. The board reads stored values and never calls GitHub while rendering.
- **Hotfixes** are `h` globs with their own counter (deferred: the design below is a sketch, not part of the first build). They are worked on a branch off the release branch and merged into it. The same ancestry check shows where they are deployed. When brought back to master, the commit message uses the hotfix ID (e.g. `s1h3: backport`).
- **Indicators:** the card shows when deployment action is required for a release environment. Production deployment is manual. Deploying to production before sign-off is allowed but should be discouraged with a warning.
- **Slop observes integration and release deployments; it only starts deploys of glob branches to their assigned environment (see Environment assignment).** Build and deploy events come from CodeBuild and CodePipeline through EventBridge. An EventBridge API destination posts them to slop's webhook endpoint with an API key header, where a driving adapter translates them into domain commands such as `BuildCompleted`, and the core never sees EventBridge.
- **Build and ATF results:** branch builds attach to the glob named by the branch. ATF runs against the integration and release environments and attach to the commit that environment was running, so every glob in that environment shows them. Details are fetched on demand through a `TestResultSource` port backed by the CodeBuild reports API.
- **Release name:** the board can optionally show which release a glob shipped in. Not needed for now.

**ATF failures:** any failing test counts as a failure. A failure is flagged clearly on the card but never blocks PR creation, PR approval, sign-off or production deployment, including ATF runs against feature branches.

**Environment assignment for product work:** each board has an enumerated list of environments; a new board starts with a single environment, main (enough for slop's own development). A glob's environment is chosen at creation (MCP input, board form, `slop new --env` or `sstor --new --env`) or at pick-up (`pick_up`, the REST pick-up and take-over actions, `slop pick-up --env` or `sstor --glob --env`; a pick-up without one keeps the glob's environment) and can be edited in the glob view at any time. There is no default, except that a board can mark one branch-deploy environment as the default for subs, which a sub created without an environment gets. Intake suggests an environment the request names (one of the board's branch-deploy environments); an explicit choice wins. **Slop starts the deploy:** when a push to a glob branch arrives through the GitHub webhook and the glob has an environment set, slop calls CodeBuild's `StartBuild` (through a `Deployer` port, using its IAM role) with the branch and target environment as parameters. If none is set, nothing deploys. Each environment has an allowBranchDeploy flag, and the core rejects assigning a glob to an environment without it. Deploys run one at a time per environment: each is pinned to an exact commit SHA (StartBuild with that SHA, never a moving branch), and while one is running only the newest pending request for that environment is kept. The environment's live state is recorded from the deploy that actually succeeded, so the board always reflects what is running. A changed environment applies on the next push, or immediately with a *Deploy now* button. Slop records which glob is live in each environment, so the card shows when another glob's deploy has replaced it in a shared environment. The base branch's own pipeline still deploys merged work to the integration environment, and release environments remain observe-only. Slop's GitHub App also puts the glob's type and environment on its PR as labels (e.g. `slop:sub`, `env:dev`) for the repo's build scripts, which decide which checks and tests run.

**Branch deploys (as built):**

- **Records, not statuses:** each request is a deploy record (`waiting`, `running`, `succeeded`, `failed`, `replaced`) in its own table; deploy state is a flag beside the glob's status and never a transition. Per environment at most one runs and one waits; a new request replaces the waiting one (`replaced`), and when the running one finishes the waiting one starts. The environment's live glob is the one whose deploy last succeeded there.
- **Triggers:** a push to a glob with an environment, in Doing, records a `request_deploy` outbox effect in the push's transaction (not for a superseded run's push or the `<id>: start` commit); the executor queues it, ignoring a repeat of the same pushed commit. *Deploy now* deploys the PR head and is open to any board member, disabled for everyone while a deploy runs in that environment.
- **Providers** sit behind a `Deployer` port and run the repo's `.sstor/deploy.sh <env>` with `SLOP_ENVIRONMENT`, `SLOP_GLOB`, `SLOP_SHA`, `SLOP_DEPLOY_ID` and `SLOP_CALLBACK_URL`. CodeBuild: `StartBuild` on the environment's project (or the board default) with the commit as source version. GitHub Actions: planned (`workflow_dispatch` plus `workflow_run` events). A deploy that can't start, or whose glob was deleted, is recorded as failed so the queue moves on.
- **Results:** CodeBuild state changes through EventBridge's API destination to `POST /webhooks/aws` (key header, one of the keys in `AWS_WEBHOOK_KEY`, since each deploy target generates its own; builds slop didn't start are ignored), and a signed per-deploy callback `POST /webhooks/deploy/{id}` that `deploy.sh` may call with `succeeded` or `failed`. Repeated results are ignored.
- **Deploy targets** (`infra`, `DeployTargetStack`): either a new CodeBuild project that runs the repo's `.sstor/deploy.sh`, or existing deploy projects whose own buildspec deploys; for those only the EventBridge rule is added, so their results come through `/webhooks/aws` alone.
- **Board:** cards show deploying or queued, live, deploy failed (with the reason, until the next success) or replaced by another glob; the glob view has Deploy now and the deploy history; board settings hold the integration (CodeBuild region, default project and per-environment projects, or a GitHub Actions workflow).

**Integration and release deploys (as built):**

- **Roles:** each environment in board settings may have a role, `integration` or `release`, independent of `allowBranchDeploy`; at most one release environment is marked production. Only environments with a role are observed.
- **Pipelines report themselves:** a pipeline that deploys the base branch or a release ref runs the catalog's `.sstor/report-deploy.sh <environment>`, which puts a `slop.ci` event (`detail-type` "Slop Environment Deployed"; detail `repo`, `environment`, `sha`, optional `ref` and `url`, `status`) on the account's default EventBridge bus. The deploy target stack forwards `source: slop.ci` to `POST /webhooks/aws` with the same key as CodeBuild events, so slop needs no read access to the board's AWS account and any CI can post the same envelope. The pipeline's role needs `events:PutEvents` (granted on a new deploy project; existing roles are set up as the board's knowledge base says). Each board whose repo matches and that has an observed environment of that name records it once per event ID (`environment_deploys`); the event's time orders deploys that arrive out of order. The key is global (`AWS_WEBHOOK_KEY`), so a key holder can report for any board's repo; per-board keys are a later hardening.
- **Containment:** a succeeded deploy that is the environment's newest queues a board-wide `check_environment` outbox effect. It asks the code host (a `CommitGraph` port, GitHub's compare API) whether the deployed commit contains each candidate's merge commit: every glob merged in the last 30 days (its latest `Merged` sha) and every glob the environment held at its last check, so rollbacks reach older globs. Results are stored per glob and environment (`glob_environments`) under a per-environment lock, and dropped if a newer deploy has been recorded meanwhile. A glob that enters an environment logs `Deployed` (`observed: true`); one that leaves it logs `DeployRolledBack`. An unknown commit counts as not contained.
- **Board:** each environment a glob is in shows as a chip on its card; a production one before sign-off is amber with a warning. The glob view lists the observed environments with whether each holds the glob and what it runs. Presence lives beside the glob (no version bump) and is refreshed by `glob.deploys` hints and on reconnect. No "not released" chip, and nothing is added to the card's status line.

**CodeRabbit results (R3, as built):**

- **Stored verbatim:** the GitHub App's `pull_request_review_comment` (created, edited, deleted), `pull_request_review` (submitted, edited) and `issue_comment` (created, edited, deleted, on PRs only) deliveries from `coderabbitai[bot]` are stored on the glob in `code_review_comments`, one row per GitHub object (external ID `coderabbit:<review|review_comment|issue_comment>:<id>`): kind `inline` (file, line or `start-end` range, commit, text, link), `review` (body, commit, link; stored even without a body, for its link), `summary` (the issue comment carrying CodeRabbit's walkthrough marker) or `comment` (any other issue comment). An edit replaces the stored text unless the stored copy is newer, so CodeRabbit's in-place summary edits are followed; a deletion hides the row and keeps it as a tombstone (`deleted_at`), so a late redelivery of the item doesn't store it again. Other authors' deliveries (including deleted "ghost" accounts with no user) are ignored before the payload is read, and a CodeRabbit delivery slop can't read is ignored rather than failed. Bodies are kept as written (cut only beyond 70,000 characters). Review comments and reviews find the glob by the PR's head branch, issue comments by PR number (including a super's PRs merged with Merge and continue), always within the board whose repo sent them.
- **Not classified twice:** only a `created` inline comment is also queued as one review finding (slice 8's `review_sources`); edits, reviews, summaries and redeliveries never are.
- **Board:** the card shows a review icon with the inline comment count, linking to the latest CodeRabbit review on GitHub (else its latest item); the glob view's CodeRabbit section lists the summary, reviews and inline comments as plain text. Stored items live beside the glob (`glob.reviews` hint, refreshed on reconnect).
- **Context bundle:** `get_context` lists the stored review as kind `code_review` and returns it in full (`codeReview`: summary, reviews, inline comments with file, line and link) with `include: ['code_review']` or `'all'`. The stored comments are indexed for search as `code_review` items (see the as-built notes under Knowledge and context).
- **Review guide:** a board knowledge document with area `review_guide` (catalog `review_guide_template`), served by `get_review_guide(repo)`. **`@coderabbitai review`:** row 11 (PR ready for review) queues `request_code_review`; its executor reads `.coderabbit.yaml` (then `.coderabbit.yml`) on the base branch, parsed as YAML, and posts the comment once per PR (a marker makes retries idempotent) only when `reviews.auto_review.enabled` is `false` and the board has a review guide. A file that doesn't parse posts nothing. The catalog's `scripts/coderabbit.yaml` is a starting config.

**ATF results (as built):**

- **Slop only observes ATF.** The board's pipeline runs it (the catalog's `buildspec-atf.yml`, a stage after a deploy, running the repo's `.sstor/atf.sh` and keeping its JUnit XML as a CodeBuild report group) and then `.sstor/atf-report.sh`, whatever the result. That counts the JUnit test cases (passed, failed or errored, skipped) and puts a `slop.ci` "Slop ATF Completed" event on the default bus (detail `repo`, `passed`, `failed`, optional `skipped`, `sha`, `url`, and an `environment` or a `branch`, or both). It reaches `POST /webhooks/aws` the same way as deploy events, and each board records it once per event ID (`test_runs`). Slop starting ATF itself (R5: before merge for sames, on ready for review for supers) is a later glob.
- **Branch runs:** a `branch` that is a glob's ID (or `refs/heads/<id>`) makes the run that glob's, on its own board only; it needs the commit it tested and logs `ATFCompleted` on the glob. It shows as stale when that commit is no longer the PR's head, and it never drives a transition.
- **Environment runs:** otherwise the run belongs to an observed environment's commit: the `sha` it reports, or the environment's latest succeeded deploy when it arrives without one. It is recorded once per board, not per glob (no events), and shows on every glob whose stored presence in that environment is contained at that commit. **Ordering against deploys** falls out of that: a run reported before its deploy's containment check shows once the check stores presence at the same commit; a run for an older commit that arrives after a newer deploy's check is kept but shows on no glob.
- **Board:** a failure is any failing test, flagged only. The card has one ATF chip (`ATF n✓`, or `ATF n failed` in red when a current run failed; muted when the only run is stale) linking to the run's report, with every run in its tooltip; it isn't part of the card's status line. The glob view's Tests section lists the branch runs and the environment runs that apply. Results live beside the glob: a branch run sends a `glob.deploys` hint, and an environment run (or a containment check at a commit that already has runs) sends one `board.tests` hint for the whole board.
- **Deferred:** the `TestResultSource` port (the CodeBuild reports API). Counts arrive in the event and the link opens the report, which covers the card and the glob view; the port comes with `get_test_results`, which needs the failing tests' names. Posting a failure summary on the PR is deferred with it.


## Time tracking and reports

Time counts only during working hours, and only toward each person's single active glob.

- **Event log:** an append-only record of every board event (moved, assigned, picked up, PR opened, merged, label changed), stored as rows per glob. Reports and aging are derived from it.
- **Active glob:** the one the person most recently moved into Doing or picked up; one active glob per person across all boards. Counting for a glob stops when it leaves Doing or another glob becomes the person's active one; an older glob does not resume automatically, only when it is re-entered or picked up again. Example: Ana picks up s1t4 at 10:00 and s1b2 at 14:00, so s1t4 gets 4 hours and s1b2 counts from 14:00. Example: a glob entered Doing on Friday at 16:00 and merged on Monday at 10:00 counts 2 hours (Friday 16:00–17:00 and Monday 09:00–10:00).
- **Working hours:** 9:00–17:00 in one configurable time zone for everyone, defaulting to UTC and shown on the board. Servers often run in UTC, so the time zone is a setting rather than the server's. Weekends are excluded; holidays are ignored.
- **Attribution:** the planner until a human implementer picks the glob up, then the implementer.
- **Reports:** monthly and yearly % RnD (features) vs maintenance (tasks, bugs) per developer. A scheduled batch job scans the event log and builds each report whole.

**Report output:** the batch job writes a CSV to S3 and the board offers it as a download. Columns: developer, period, RnD hours, maintenance hours, % RnD.

## Data, auth and infrastructure

Slop is one portable Docker image running as a single instance, backed by Postgres. AWS-specific services sit behind adapters, so the image can move to any host; sign-in is the one remaining AWS tie.

| Concern | Choice |
| --- | --- |
| Hosting | One container (Node with Hono or Fastify) on a small EC2 instance with an IAM instance role, run with Docker Compose alongside Postgres. The same Compose file runs locally. |
| Frontend | Vite + React + TypeScript, Tailwind + shadcn/ui, dnd-kit, served by the same container. The board is built from scratch rather than adapting an open-source kanban app; community shadcn-based kanban components can serve as a starting point |
| API | REST, MCP, webhooks and live updates all served by the one server |
| Database | PostgreSQL with full-text search and pgvector, holding globs, events, communications and search. Runs in Docker (official Postgres image with pgvector) on the same EC2 instance. Aurora Serverless v2 is the managed alternative if point-in-time restore is ever needed. |
| Migrations | Drizzle, run on deploy |
| Live updates | Server-sent events from an in-process notifier |
| Artifacts | S3-compatible storage with bucket versioning, served via presigned URLs |
| LLM and embeddings | Amazon Bedrock behind the LLM port (Claude Haiku 4.5 for intake, Opus 5.5 for the KB pipeline); a direct Anthropic API adapter is possible |
| Sign-in | Cognito federated to IAM Identity Center |
| GitHub | GitHub App with installation tokens; source stays on GitHub |
| CodeBuild events | EventBridge API destination posting to slop's webhook with an API key header |
| Secrets | Environment variables for configuration; Secrets Manager for sensitive credentials (GitHub App key, routine fire tokens), read via the EC2 instance role |
| Infrastructure | CDK for the AWS resources (Cognito, S3, IAM, EventBridge, host) |

**Auth**

- **Board:** the server handles the Cognito login (federated to Identity Center) and keeps a server-side session cookie (30 days). The OAuth `state` is signed by the server and bound to the browser by a nonce cookie, which stops login CSRF. A plain-http `localhost` dev server can accept the signed state without the cookie, because Chrome drops it on the cross-site return from Cognito; that exception is off unless the server is started with `LOCAL_SIGN_IN_WITHOUT_COOKIE=true` (`scripts/dev.sh` sets it), so a proxy rewriting `Host` to `localhost` can't open login CSRF on a deployed slop.
- **Claude app connector and routines:** Cognito is the OAuth authorization server, using a pre-registered app client whose ID and secret go in the connector's Advanced settings, with callback `https://claude.ai/api/mcp/auth_callback`. Routines use the account's connector.
- **Claude Code:** OAuth login against Cognito via `claude mcp add --client-id`, once in the browser, then automatic refresh.
- **Sessionator (the slop CLI):** the same public client as Claude Code, with its own callback (`localhost:7780`): `sstor login` runs the authorization code flow with PKCE once in the browser, keeps the tokens in the macOS Keychain and refreshes automatically. sstor calls slop's `/mcp` directly with the access token; it never starts a Claude session to reach slop.
- **Slop verifies Cognito JWTs** with `aws-jwt-verify`, checking issuer and client ID, and publishes the protected-resource discovery document pointing clients at Cognito.
- **Integrations** use per-integration secrets, not user sign-in: a per-user ingest secret for the Apps Script (it also identifies the user), the Slack app's signing secret, the GitHub App webhook secret, and an API key on the EventBridge connection. **Public endpoints:** only the script catalog is served without authentication; it is board-agnostic and contains nothing sensitive or project-specific. The agent set is board knowledge, fetched through the authenticated MCP. Everything specific to a board, including its knowledge, settings and review guide, stays behind OAuth. There is no board token.
- **Roles live in slop.** Identity Center only answers who someone is; email is the stable user ID, with Cognito's user ID and the GitHub username stored against it.
- **Offboarding:** removing someone from Identity Center blocks new logins; a deactivate action in slop rejects their requests immediately.
- **Cognito plan:** Lite. Federated users are free up to 50 monthly active users.
- **Local development:** a dev Cognito pool in CDK with native test users; agents get real tokens with `aws cognito-idp initiate-auth`, and slop validates them exactly as in production.
- **Fallback:** if the connector checks fail, slop becomes its own authorization server (MCP SDK helpers, with dynamic client registration) and Cognito handles login only; Keycloak in the Compose file is the alternative.

**Token lifetimes:** access tokens last one hour and refresh silently; the Cognito app clients for the Claude connector and Claude Code use the maximum refresh token lifetime (10 years), so each person logs in once. Every MCP request is still authenticated. A leaked refresh token is handled by slop's deactivate-user action (slop rejects deactivated users regardless of token) and by revoking the person's tokens in Cognito.

**Search**

- **Communications** (meeting notes, chat threads) are an entity: metadata and text in Postgres, raw files in S3, linked to any number of globs.
- **Ingest** uses one canonical format, `IngestCommunication { source, sourceId, author, occurredAt, title, text, participants }`, on a generic endpoint authenticated by the per-user ingest secret. Scripts (Apps Script, exporters) send that format; only sources with fixed formats, such as the Slack app, get a dedicated adapter. Repeats are ignored by `sourceId`.
- **Indexed content:** communications, glob summaries and plans, implementation records and KB entries, with board, glob, source, person and date as metadata. Search is per board.
- **Keyword** search uses Postgres full-text search; **semantic** search uses pgvector with Bedrock embeddings. Both sit behind the `SearchIndex` port and update when data is saved.
- **One chat-style input on the board:** the question goes to Claude via Bedrock with `search_text`, `search_semantic` and `get_glob` tools scoped to the board; Claude chooses the searches and answers with links to the globs and meetings it used. Responses stream.

**Not chosen:** Lambda, DynamoDB, AppSync, Amplify Gen 2 backend tooling, Bedrock Knowledge Bases on S3 Vectors (semantic search only), OpenSearch Serverless (minimum cost), Supabase, Firestore, PocketBase, Convex, Keycloak (kept as fallback), Aurora Serverless v2 and Neon (Postgres on the VM chosen), Fargate, Lightsail (no instance IAM roles), Google Workspace sign-in, CodeCommit, and App Runner (closed to new customers since 30 April 2026).

## Board notifications

One bar across the top of every board page shows board-wide incidents that need a person. It is not per-glob status. Board setup (readiness) is on it too, quietly: its severity follows the item's state, so setup that can wait for weeks never sounds like an incident.

- **Model.** A `BoardNotification` has an `id` (`<board or all>/<source>`), `boardId` (null for every board), `source` (`main-red`, `integration:<id>`, `local-follow`, `readiness`, `readiness:<item>`), `severity` (`critical`, `warning`, `info`), `title`, `detail`, `link`, an optional `action` (label and href), `since`, and how it clears: `condition` (its source clears it), `until` (a time) or `dismissible` (for everyone) or `personal` (for the person who dismisses it). A `personal` one lists the `items` it is about and, per person, the items they had seen when they dismissed it. There is one per board and source; raising again replaces it and keeps its `since`.
- **Storage.** Beside the board, with no glob or board version. Sources raise and clear through the core `NotificationSink` port, implemented by `NotificationService`, which sends a `board.notifications` hint on every change. Expired `until` notifications are dropped on read. Only `dismissible` and `personal` ones can be dismissed; a personal dismissal is stored per person on the notification itself (not in the browser), with the items it covered, and the notification returns for that person when an item joins its set.
- **Delivery.** The board refetches on the hint and on every live-update reconnect, and polls every 15 s while one is showing (60 s otherwise), because a hidden tab closes its event stream and loses hints.
- **The bar.** Critical is large and red, flashes once when it arrives and cannot be dismissed while its condition holds. Warning is amber. Info is quiet. With several, the most severe (then the oldest) shows in full and the rest as a "+N more" count that expands.
- **Main is red (critical).** Raised when the base branch's checks fail and cleared when they pass, from the same read that records `board.baseChecks`. It names the failing check and its first error, the glob whose merge turned the base red, and that globs failing the same way are waiting. It links to the failing run.
- **Board setup (readiness).** A readiness item that is **failing** (it worked and now doesn't) raises a **warning** `readiness:<item>` with the item's detail and fix, linking to the checklist (`/boards/<id>/settings#readiness`); it clears itself when the item passes. Items **missing** (never set up) raise one **info** `readiness`, "Board setup: N items to do", linking to the checklist; it is `personal`, so each person dismisses it for themselves, and it returns when a new item becomes missing. Unknown and ok items raise nothing. The server checks every board each minute and whenever the checklist is read, from the same facts the settings checklist shows. The full checklist stays in board settings; there is no separate readiness banner.

## Operations

Slop has two environments: a developer's laptop (Docker Compose) and production on EC2. Only production is backed up.

- **Backups:** a nightly `pg_dump` to S3 kept for 30 days by a lifecycle rule; a weekly EBS snapshot via AWS's snapshot scheduler; artifacts protected by S3 bucket versioning. One test restore after setup. Cost is well under a dollar a month.
- **Deploying slop:** CodeBuild, triggered by pushes to main, builds the image, pushes it to a registry, and updates the EC2 instance through SSM Run Command (no SSH, no stored keys). Migrations run when the app starts. CodeBuild is preferred wherever it fits.
- **System page:** the last \~100 errors (stored in Postgres, with time, task and message); when each automatic input was last received (GitHub and AWS webhooks, each person's Apps Script, the Slack app); the last routine run per person; the last report run; the indexing backlog. Anything silent for longer than expected shows amber.
- **Uptime:** a free external uptime checker pings the server and emails when it is down.
- **LLM spend:** slop multiplies its own token usage by a price table and shows month-to-date spend as a small line on the board. An AWS Budgets email alert is the backstop. No per-user caps for now.
- **Data retention:** everything is kept by default. Any item can be deleted, and a "remove everything from this source or person" action handles departures and requests. Each deployment should check its personal-data retention obligations under the data-protection law that applies to it.

## Testing

Slop will get little human review, so automated checks act as its reviewers.

**Slop's own code**

- Strict TypeScript and linting, including the boundary rule that keeps adapters out of the core.
- Unit tests for core rules: the category/type matrix, transitions, sub-to-same conversion, label rules, ID generation, ancestry-based deployment status and time calculation. The core runs against in-memory fakes, so these are fast.
- A few Playwright smoke tests: load the board, move a glob, open an artifact.
- A short human look at the security surface even so: Cognito and Identity Center setup, IAM grants in CDK, and the GitHub App's permissions, especially its right to merge to master.

**Test results for the repos slop manages**

- Tests and snapshot or golden files are committed; run output is not.
- CodeBuild report groups hold the results (JUnit XML, LCOV or Cobertura), with raw files exported to S3 for longer retention.
- Slop reads results through the CodeBuild reports API and shows them via the glob's test icon. Branch results attach to the glob; ATF results attach to the environment's commit.
- A failure summary is posted on the PR so reviewers and Claude's auto-fix can act without AWS access.

**Local environment**

- Docker Compose runs the app and Postgres; Claude Code can start it, run tests and drive the board with Playwright.
- A dev Cognito pool with native test users provides real tokens; local Claude Code connects to the local MCP with one.
- GitHub and AWS events are tested by replaying saved real payloads; anything that creates branches or PRs uses a test GitHub App on a sandbox repo.
- Storage and Bedrock use real dev resources with a dev AWS profile. In-memory fakes are used only for core unit tests.

## Supers

Pairing work is at the developer's discretion, including up to 2 days before marking the PR ready; the aging colour applies as for any glob.

- The developer works on the glob's own branch throughout. Each push deploys it to the glob's environment (normally a branch-deploy environment the developer uses), started by slop.
- The local review runs in sessionator using the slop-delivered agents and is pushed to slop as the `local_review` artifact.
- The glob's draft PR exists from creation (supers start in Doing). It is marked ready for review through slop's `mark_ready`: in the session after `/finalise` (which `sstor --ready` sends), or with the board's Ready for review, which warns when no local review is recorded at the head. That triggers ATF and the remote review; results reach slop through the existing webhooks and EventBridge.
- Developers choose the glob's environment from the board's branch-deploy environments. Slop tracks no environment claims; the card shows when another glob's deploy has replaced this one in a shared environment.
- **Branches:** every glob has its own branch, always created from master. No stacking: if reviews send back serious problems, work does not continue on a new glob until they are resolved.
- `sstor --new --super` creates the glob (through `create_glob`, which returns `{ id, branch }`) and opens a session on its branch.
- **Implementation record:** sessionator updates the record from the code changes and the session conversation on each push (best effort) and always at sstor --ready and --derge, and sends it to slop. When the meeting ends and its Gemini notes arrive through the Apps Script, slop suggests attaching them to the developer's active super, a person confirms, and slop then runs one more pass merging the meeting's decisions into the record.

## Roles and permissions

Board roles are admin, dev, QA and PO.

- Roles are per board, stored on the membership record (user + board).
- Anyone can create a board; its creator is its admin. New members default to dev.
- Only admins add users and set roles; admins can do everything.
- Anyone on the board can delete globs. FR, CR and QA can only be switched on the board, not through the MCP.
- QA and PO can create subs and sames, but not supers, and they cannot pick up (or take over) sames or supers.
- Users are added by email and linked to their account on first sign-in.
- **Board settings:** repo, base branch (e.g. master or main), sensitive paths, time zone, default routine owner, environments with their allowBranchDeploy flags (and at most one, allowing branch deploys, marked as the default for subs) and roles (integration or release, with at most one release environment marked production), members and roles. Wherever this document says master, it means the board's base branch.
- **Board readiness:** board settings show a checklist of what the board needs before slop can run its globs end to end: slop's GitHub App on the repo, the `sub-gate` and `checks` workflows on the base branch (both required checks), a workflow on the base branch that runs `anthropics/claude-code-action` (what makes `@claude` comments get a response; catalog `claude.yml`, or `/install-github-app`), the agent set committed at the board's version (`.claude/slop-agent-set.json`), a build doc, branch-deploy environments with a default for subs, and three items slop can't check (routines for the board, the repo in the routine's repositories, the Claude GitHub App itself), which an admin ticks and which turn red when a routine failure in the last week points to them. Each item has a Fix link, and the board shows a banner while anything needs doing. Cards show a stuck hint for a ready sub with no gate result after 15 minutes, a passed gate that hasn't merged, or a routine failure with a known fix. What each environment is for goes in an environments KB document (catalog template).
- **MCP access:** slop's MCP is a claude.ai custom connector with Cognito as the OAuth server (see Auth). The Claude app and routines act as the signed-in person with their board role; Claude Code and sessionator log in the same way.
- No notifications outside the app for now.

## Planning inputs and intake

- **Attach** through the MCP as inline text or links; on the board as text, links or file uploads. Links (Google Drive, Slack) are fetched by a `SourceFetcher` port and stored as snapshots. Files are only uploaded through the board.
- **Meeting inbox:** every meeting arrives through its source's adapter and is stored once. An LLM suggests attaching it to existing globs, across boards, or creating new globs from its action items; a person confirms. One meeting can attach to several globs. No automatic attachment to start with. Meetings come from Google Meet notes.
- **Related meetings:** intake searches slop's stored meetings by keyword (semantic search later), not the meeting tools directly.
- **Artifact history:** S3 bucket versioning, with a current-version pointer on the glob. No git.
- **LLM:** Amazon Bedrock via the Converse API, called with slop's IAM role behind the LLM port; prompts live in the core. Claude Haiku 4.5 for intake and meeting classification to start; Opus 5.5 for the KB pipeline. Credential and access failures (an expired AWS sign-in, missing Bedrock permission or model access, a model that isn't found, enabled or valid, no credentials) are a typed *LLM unavailable* condition, not a generic error. The fix names what to do: `aws sso login` with the profile when `AWS_PROFILE` is set, otherwise the server's IAM role; for a model problem, its setting (`INTAKE_MODEL`, `KB_ROUTE_MODEL`, `KB_DRAFT_MODEL`, `CHAT_MODEL`) and model access in the Bedrock console. A model ARN's account ID is masked. Slop tracks health per model and logs each change; `GET /api/health` (members of any board) returns the worst state: ok, down with a plain-language reason and fix, or unknown, with no profile, region or model fields. Intake answers `llm_unavailable` (HTTP 503) with the fix. Throttling, overload, a model not ready, quota bursts, server errors and SDK timeouts are a separate *Bedrock busy* condition (`LlmBusy`): callers wait and retry with backoff, it never marks a model down or raises the AI-paused banner, and the Bedrock clients use adaptive retry with 5 attempts; ten busy answers from one model within ten minutes raise a warning ("Bedrock is throttling <model>") that the next success clears. Other model errors are ordinary failures.
- **Intake inference** returns name, summary, type, category, group (existing preferred), an environment the input names (one of the board's branch-deploy environments, matched as a word) and `autoTrigger` with a reason, validated against the matrix with safe defaults. Through the MCP, explicit fields win. Sames auto-trigger only on an explicit instruction in the input.
- **Create on the board:** a free-text box with attachments and a Process button; the LLM fills a structured form (name, summary, type, category, group, auto-trigger) that the user checks and edits before Create. The form can also be filled directly.

* **Meeting sources:** Google Meet notes via Apps Script. Each person's script uses their own ingest secret. Meetings arrive without a board, in a shared inbox every slop user can see; once attached to a glob they also appear on that glob's board. Attachment is always confirmed by a person. The inbox has a discard action for meetings that don't belong.
* **Other sources** (Slack threads, pasted text, legacy docs) post the canonical ingest format; see Knowledge and context.

## Knowledge and context

Slop is a context manager: it holds what is known about the work, decides what is current and relevant, and serves curated context to people and agents.

**Knowledge sources**

| Source | Stored | Chunking | Best queried by |
| --- | --- | --- | --- |
| Meetings | Gemini notes; transcripts too for formulation meetings | Notes by section; transcripts in \~500-token windows | Text and semantic search, by date and participants |
| Slack threads | The thread with author names kept in every window, plus an LLM summary of its conclusion and each participant's position | Summary as one chunk, plus windows of consecutive messages | Text and semantic search |
| plan.md and implementation records | Every version; older versions marked superseded | By heading | `get_plan` with history; search |
| Code changes | Per merged glob: commit SHA, PR link, changed file paths and an LLM summary of what changed and why; full diff fetched from GitHub on demand | One chunk | `search_changes` (summaries plus trigram match on paths, by date); agents also use `git log -S` / `-G` |
| Build failures | Only the error messages (the first piece is recorded on the glob's head checks, see Merging) and what failed, written by an LLM from the tail of the failing build log and the test report | One chunk plus structured rows | `get_build_results` |
| Test runs | Structured rows: glob, commit, environment, counts, failing test names and messages | Not chunked | `get_test_results` |
| Legacy Jira issues | Description, comments, linked commits and a "why this changed" summary | One chunk, split if long | Search (legacy tier) |
| Legacy Google Docs | The document | By heading | Search (legacy tier) |
| Decisions | Their own items, linked to their source | One chunk | Search; shown on globs |
| Knowledge base | Lives in slop, versioned in Postgres, per board. Each document has an area and an audience (the agents that must always be given it). Served only through MCP tools; agents save what they fetch under `.reviews/` for the session. Slop indexes it directly | By heading | `get_conventions`; search |

**Knowledge delivery:** slop is the source of truth. `sstor init <board>` runs before Claude starts whenever sessionator creates or syncs an instance: it fetches the board's agent set with `get_agent_set`, using sstor's own sign-in, and writes it into the checkout, where it is committed (see Agent system). On a first install it writes the slop server entry into `.mcp.json` from sstor's own configuration (slop's URL and the Claude Code client ID, neither sensitive), so Claude Code can authenticate. Routines use the committed agent set and refresh it from the orchestrator. The board ID comes from an argument, an environment variable, or `.sstor/sstor.conf` (`SLOP_BOARD`). If slop is unreachable, the committed copy is used with a warning. All other board knowledge (build commands, conventions, architecture, decisions, history) and the board's settings are fetched at run time through the MCP tools (`get_board`, `get_context`, `get_conventions`, the search tools), authenticated by the connector's OAuth. Existing project docs (e.g. a project's `.sstor/docs/`) are imported into the board's knowledge base once, then removed from the project repo. Review guides are also served from slop rather than the repo (see Review and testing). Details are in the sessionator document.

- **Card search and content search are separate.** Board filters find globs by structured fields; the chat and agent tools search content. The chat can use both.
- **The current codebase is not indexed.** Agents with a checkout use grep and git; slop holds the history of changes, not the code. GitHub's own MCP server can complement slop's tools for code and PR search.
- **Raw diffs are not indexed.** Change summaries are generated with one cheap LLM call per merged glob.

**Order of authority** when sources disagree: merged code and the implementation record, then current decisions (newest first), then plan.md, then older discussion. Superseded decisions are history, not instructions. A decision is a later, explicit choice, so it outranks the plan it amends. Context bundles state this order (`authority`) and carry the glob's own decisions.

**Decisions and supersession**

- On ingest, an LLM extracts decisions from each communication (statement, topic, date, source) and compares them with existing decisions on the same topic.
- A contradicting newer decision marks the older one `superseded`, linked to its replacement. Superseded items are not hidden: they are heavily down-ranked and labelled "superseded by…" with a one-line reason, so readers and the LLM see both the history and what is current. Supersession is judged by an LLM comparing a new decision with the most similar active decisions on the board; plan versions supersede each other automatically.
- Decisions appear on the glob with their sources. Members confirm or undo a replacement (as built below); marking a decision wrong is not built yet.
- Newer material ranks higher when relevance is equal.

**Context assembly**

- A core use case, `assembleContext(glob, purpose, tokenBudget)`, returns a cited bundle: the plan, the implementation record, active decisions linked to the glob or its topic, the most relevant recent communication excerpts, related past globs with their change summaries, current test results and relevant conventions.
- It serves routines and sessionator (`get_context`), plan drafting for sames, glob generation from inbox meetings, and the board chat.
- Two modes: slop pushes a curated bundle; agents pull anything further through the search tools.
- **Plan and record in full.** `get_context` always includes plan.md and the glob's implementation record (when one exists) in full, and attachments labelled Clarifications or Assumptions in full (they carry intent that agents must follow and pass verbatim). Every other artifact (local reviews, other attachments) is listed with kind, label, version, commitSha, size and a one-line description, so a revisited glob doesn't flood an agent's context with overlapping documents. CodeRabbit's stored review of the PR is listed the same way (kind `code_review`). `include` (e.g. `['attachment:Notes', 'local_review', 'code_review']`, or `'all'` for everything) returns the named artifacts in full, and `get_artifact(id, kind, label?)` returns one artifact's latest version. The record is the response's `implementationRecord` (version, commitSha, content).
- **One implementation record per glob.** Every glob, of every type, has plan.md (the planner's intent and "Done when") and one implementation record in the same format: Approach, Decisions (each with why, rejected alternatives and trade-offs), Deviations (from plan.md, with reasons), What was built (by area, with commits), Traps and Open items. It is stored as the `implementation_plan` artifact (an agent set may still write `postplan`, an alias for the same record) and kept up to date as work proceeds: started in Phase 2 from the chosen proposal (the investigator's alternatives stay in the local plan file), updated in Phases 3–5, completed and pushed with the HEAD commit in Phase 6, and for supers started at the first agreement and pushed after each push and at finalise. Migration `0026` made each existing glob's latest postplan the next version of its record; where the glob also had a decision log (s15f5), the log is kept below the postplan in the same document, with the older versions as history.

**In the architecture**

- Core modules alongside the board: **Knowledge** (sources, decisions, supersession), **Context** (assembly and ranking) and **Generation** (globs and plans), using the existing `SearchIndex` and LLM ports.
- Postgres holds it all: a `knowledge_items` table with `source_type`, `occurred_at`, `created_at`, glob links, `status` and `superseded_by`, and a chunks table with full-text, trigram (`pg_trgm`, for identifiers) and vector indexes.
- Added MCP tools: `get_test_results` (by glob, commit or environment) and `get_change` (summary, files and optionally the diff for a glob).

**Build order**

1. Glob, plan and communication search, plus a basic context bundle ranked by authority and recency.
2. Code change summaries and test result tools.
3. Decision extraction and supersession.

**Search modes:** searches take a mode. **Current** (default) favours recent material, heavily down-ranks superseded items and ranks legacy last. **All time** removes recency weighting and includes superseded and legacy items, labelled with date and status. An optional date range applies to both. The chat switches to all-time mode when a question implies older discussion; the board has an *Include history* toggle; the MCP search tools take the same parameter.

**Chat**

- Conversations, messages, tool calls and citations are stored in Postgres per user per board. Recent turns are sent each time; older turns are summarised.
- Chat answers are never indexed automatically; a *save to knowledge* button lets a person keep one.
- The agent loop is plain code in the container using Anthropic's TypeScript SDK with its Bedrock client, so it can switch to the direct Anthropic API by configuration. AgentCore is not used.

**LLM usage and cost**

| Workload | Model | Expected cost |
| --- | --- | --- |
| Embeddings | Bedrock Titan Text Embeddings V2 | Negligible, including the backfill |
| Ingest processing (decisions, change summaries, classification, intake) | Haiku 4.5 | A few dollars a month |
| KB pipeline (routing, dedupe and drafting of learnings) | Opus 5.5 | Cents per learning |
| Chat and context assembly | Sonnet 5.5 for chat as built (`CHAT_MODEL`); Haiku by default for context assembly; Sonnet for plan drafting or on request | Tens of dollars a month, depending on use |

- Prompt caching for the chat's system prompt and tools; a cap on tool steps and retrieved tokens per question; batch inference for the backfill; usage tracked per feature with an AWS Budgets alert.
- No self-hosted LLM. A small open embedding model on CPU in the container is an option if portability ever outweighs quality.
- Search quality levers: structure-aware chunking, a source/title/date/glob header on each chunk, and a reranker (e.g. Cohere Rerank on Bedrock) if needed. ParadeDB's `pg_search` adds BM25 ranking if Postgres full-text ranking proves weak.

**Inputs**

- **Paste:** an *Add to knowledge* box on the board and an `ingest_text` MCP tool, so the Claude app can save a conversation, optionally linked to a glob.
- **Google Meet notes:** the Apps Script polling each person's Drive for Gemini notes and transcripts.
- **Slack:** a small Slack app with a *Send thread to slop* message shortcut (or a `:slop:` reaction); each thread is one communication. Channel-level ingestion can come later. A workspace admin approves the app's installation.
- **Legacy Google Docs:** a one-off Apps Script import, tagged legacy.

**Backfill (legacy tier)**

- Import every issue from the team's previous issue tracker (Jira is the first importer), with descriptions and comments, and the commits linked to each issue, as knowledge items, not globs.
- Generate one "why this changed" summary per issue from its text and linked commits, in batch.
- Skip commits without an issue link; agents find them with `git log`. Skip CodeBuild history.
- Legacy items keep their original dates, rank lowest, are excluded from context bundles unless nothing newer covers the topic, and are never used for decision extraction. The import window is chosen per board (e.g. the last 12–18 months).
- Decision extraction runs only on recent communications (about the last three months).
- All imports go through the canonical ingest endpoint via scripts, oldest first.

**Storage and search configuration** (starting point, to be tuned on real data)

- **Tables:** `knowledge_items`, one row per source item (board, `source_type`, title, `occurred_at`, `created_at`, authority tier, status, `superseded_by`, linked globs, external reference, text or S3 key for large originals); `chunks` (item, position, header, text, full-text, trigram and vector indexes); structured `test_runs`, `test_failures` and `build_failures` tables.
- **Chunk headers** contain only stable facts known at ingest: source type, date, title and section, e.g. `[Meeting · 2026-09-14 · "Sync retry design" · Decisions]`. Missing titles are written by the ingest LLM pass. Glob links are filterable metadata, not header text, so linking never forces re-embedding.
- **Chunk sizes:** about 300–600 tokens; Slack threads kept whole up to about 1,000 tokens.
- **Language:** English full-text configuration. Content in other languages still matches exact words and works in semantic search (Titan V2 is multilingual).
- **Embeddings:** Titan Text Embeddings V2, 1024 dimensions, cosine similarity, HNSW index in pgvector.
- **Keyword search:** Postgres full-text search plus a trigram index for identifiers, error strings and file paths.
- **Ranking (current mode):** recency decay with a 90-day half-life; authority weights; superseded items heavily down-ranked and labelled; legacy demoted. All-time mode removes recency decay.
- **Board search box:** reciprocal rank fusion of keyword and semantic results. **Chat:** Claude chooses among the tools; Cohere Rerank on Bedrock reorders the top 50 to the best 10.
- **Retrieval budget:** at most about 10 chunks or 8,000 tokens per search call.
- **Chat and agent tools:** `search_text`, `search_semantic`, `search_changes`, `get_glob`, `get_plan` (with versions), `get_change`, `get_build_results`, `get_test_results`.
- **Volume:** sized for a small team, around 7 hours of meetings a week; ingest costs stay at a few dollars a month.


**As built (slice 8, search store)**

- **Store:** migration `0023_search_store` creates the `vector` and `pg_trgm` extensions, `knowledge_items` (unique per board and `external_ref`; `body` and `body_key` exist but are unused, text lives in chunks) and `chunks` (generated English `tsv`, `vector(1024)` with an HNSW cosine index, a trigram index on the text, a partial index on chunks still waiting for an embedding). Chunks carry `board_id` too, and every query filters on it.
- **Indexed so far:** glob summaries, the latest plan, implementation record, local review and attachments of each glob, CodeRabbit comments, board knowledge documents, approved learnings (other than decisions, which are indexed as decisions), one change summary per merged commit, and decisions (see the decisions notes below; they are written by `DecisionPipeline`, not by the indexer). Pasted inbox items (source types `meeting`, `thread`, `doc`; see the inbox notes below) are written by `InboxService`, not the indexer. Slack, Jira and legacy imports have no producer yet; the `legacy` status is in place and exercised by tests only. Only the latest version of a plan is indexed.
- **Sync:** the index is derived. `SearchIndexer` compares a content hash per item and rewrites only what changed (the start-up run is the backfill); a board is re-synced about 10 seconds after a change to its material and every 15 minutes regardless, so results lag writes by that long. Embedding runs after the keyword rows exist, so text search works first and semantic coverage fills in. While Bedrock is unavailable, chunks keep a null embedding, nothing fails or counts an attempt, and the job probes once a minute. A merged change is queued searchable by title, then Haiku writes its "why" from the glob's plan and the changed files (at most 150 words; it waits the same way).
- **Authority weights:** merged code and implementation records 1.0, decisions 0.95, approved plans, knowledge and learnings 0.9, discussion (reviews, attachments, CodeRabbit) 0.6, legacy 0.3. Score = relevance x authority x recency x status; recency halves every 90 days and superseded items count 0.15, both only in current mode; legacy sorts after everything else in current mode.
- **Chunking:** headings split sections, paragraphs pack to about 450 tokens (300 minimum, 600 maximum), no overlap.
- **Tools and route:** `search_text`, `search_semantic` and `search_changes` and `GET /api/boards/:b/search` (`q`, `history`, `from`, `to`, `glob`, `group`) all check board membership first. The route fuses keyword and semantic results (reciprocal rank fusion) and returns `semantic: "unavailable"` with keyword results when the embedder is down; the board header has the search box with an *Include history* toggle.
- **`get_context` `related`:** the bundle gains `related`: up to five cited results for the glob's title and summary in current mode, without the glob's own items. The semantic arm queries with title and summary and the keyword arm with the title only; with the embedder down or slow (5 seconds) it is keyword-only. Existing fields are unchanged.
- **Not yet:** reranking, the S3 body key, and the other sources above (chat is built: see the next section).

**As built (slice 8, board chat)**

- **What shipped:** a chat panel opened from the board header (beside the search box), and `ChatService` in core. A question runs one retrieval, then one model call. Retrieval is the board search box's (keyword and semantic fused, keyword alone while the embedder is down), in current mode, or all-time with *Include history*, optionally scoped to a glob or a group; decisions are indexed items, so they come back ranked by the usual authority, current ahead of superseded. The top results are numbered and sent to the chat model (`CHAT_MODEL`, default Sonnet 5.5 through Bedrock, no sampling parameters, 60-second deadline, tracked in model health like the others, usage in the `[llm]` log line) with the last six turns for follow-ups; retrieval uses the current question only. The model answers in JSON (`answer` with `[n]` markers, and `used`, the numbers it relied on).
- **Citations are built by the server** from the retrieved results the model says it used, never from model text: a number that matches no result is dropped, and each citation carries source, title, date, link, glob and status; a superseded decision also carries the newer decision's title and date, which the panel shows as "superseded by ..." and links when it can. When nothing is retrieved, when the model uses no source or its answer isn't usable JSON, the reply is "I don't know from the board's records." with no citations; with nothing retrieved the model isn't called.
- **Storage and routes:** `board_chat_messages` (migration 0029), one conversation per person per board (a member never sees another's). `GET /api/boards/:b/chat` returns the last 50 messages, `POST` takes `question` (at most 2,000 characters), optional `history`, `glob`, `group` and returns the question and reply messages, `DELETE` clears the conversation. A busy or unavailable model answers 503 `llm_unavailable` with the reason and fix, and nothing is stored, so the person asks again; the panel tells busy ("Bedrock is busy") from down. Members only.
- **MCP:** `ask_board(board, question, globId?)` returns the answer and its citations without reading or writing the person's conversation.
- **Not built:** the agentic tool loop (Claude choosing searches and `get_glob`), streaming, summarising older turns, *save to knowledge*, reranking, choosing all-time automatically from the question, and prompt caching or a per-question token cap beyond the retrieval budget.

**As built (slice 8, decisions and supersession)**

- **Where decisions come from:** the text under `## Decisions` of each glob's implementation record (or legacy postplan), the whole of plan.md, and attachments labelled Clarifications or Assumptions (the latest version of each), plus approved knowledge items of type `decision`. Attached inbox items (see the inbox notes below) are read as sources too; Slack has no producer yet. The learning is a decision without a model call: its statement is its own quote, its date and author are the approval's. Such a decision has no glob and links to the Knowledge page.
- **Tables:** migration `0027_decisions` adds `decisions` (one row per decision, with the knowledge item it is searched by, glob and group, statement, verbatim quote, who and when, source kind, ref, label and link, and its supersession: `replaced_by`, `replace_state`, the two quotes and a reason, `checked_at` and the check's retry state) and `decision_sources` (per board and source ref: the content hash last extracted, `pending`, `done` or `failed`, attempts, `process_after`, last error). A decision's knowledge item has source type `decision`, authority `decision` and external ref `decision:<source ref>:<12 hex of a hash of its normalised quote>`, so an edited source keeps the decisions whose quote is still in it. Deleting a glob deletes its decisions and releases older decisions they replaced.
- **Extraction:** `DecisionPipeline.syncBoard` (run for a board about 10 seconds after a change, at start and every 15 minutes, like the index) hashes each source and queues the new or changed ones; `processNext` extracts one per call with one Haiku call (the search model, `SEARCH_MODEL`; job `decisions`, paused with that model). The answer is a strict JSON list of statement, quote, who and date. A decision is kept only when its quote is found word for word in the text shown to the model (case, whitespace and sentence punctuation at the ends ignored) and is at least four words and 20 characters; no quote means no decision. At most 40 decisions per source and 30,000 characters per source are read. The date is the model's only when it parses as an ISO date, else the artifact's date. Re-running changes nothing; a changed source replaces its decisions and keeps the status and replacing decision of those still quoted; a decision whose quote left the source is deleted. While the model is unavailable a source waits (a minute, or a growing wait when Bedrock is busy) without spending attempts; other failures retry with backoff and fail after three attempts.
- **Supersession:** each new decision is checked once, after the sources are extracted. Candidates are active, earlier (not later than the new one) decisions on the board that are near it by keyword search or, when the embedder works, by meaning (similarity 0.75 or more), then those on the same glob or group, at most six. One Haiku call names the candidates the new decision contradicts or replaces, each with a quote from the old and the new decision. A replacement is applied (the old decision's item becomes `superseded`, linked to the new item) only when both quotes are found verbatim in the decisions' own text and are long enough, the old decision is still active and the new one is not itself superseded (so no cycle); a valid candidate whose quote fails is stored as a hint (`replace_state` `hint`) and changes nothing. A pair a person undid is never applied again. States: `hint`, `applied`, `confirmed`, `undone`. An embedder failure only drops the semantic candidates; a model that is unavailable makes the check wait without spending attempts, and three failures count the decision as checked.
- **Person control:** `GET /api/boards/:b/globs/:g/decisions` lists the decisions taken on a glob (members), each with its source link and what replaced it and what it replaced; `POST /api/boards/:b/decisions/:id/confirm` turns a hint into `confirmed` and supersedes the older decision; `POST .../undo` turns an applied, confirmed or proposed replacement into `undone` and the older decision is active again. The glob view shows them under Decisions: a superseded one struck through with "Superseded by ... on <date>", a hint as "Proposed: replaced by ..." with Confirm and Dismiss. A `glob.decisions` hint refreshes the list.
- **Search and context:** `decision` is a source type (label "Decision"). In current mode a current decision ranks above every superseded decision, and superseded results are labelled `superseded by "<title>" on <date>` (with `supersededBy: {title, date}` on the hit); all-time mode shows both with the labels and no penalty. `related` in `get_context` puts up to three current decisions on the topic first, then the other hits (superseded decisions labelled), at most five in all. The bundle also has `decisions` (the glob's own, current first, each with its source and what replaced it) and `authority` (the order of authority above). The search indexer never removes decision items.
- **Not yet:** decisions from Slack, marking a decision wrong, and re-checking supersession for an old decision when a newer one is edited, and comparing a decision with earlier-dated decisions that arrive after its one check.

**As built (slice 9, inbox and paste)**

- **Scope:** the board inbox and paste only. Meetings from Apps Script, Slack and the other adapters, the cross-board shared inbox, and *create glob from an item* are later parts of slice 9. Routes are board-scoped (`/api/boards/:b/inbox...`), not the global `/inbox` of the interface table: every other store and route is per board, and paste is the only producer so far. Attaching is to globs on the item's own board.
- **Tables:** migration `0029_inbox` adds `inbox_items` (the pasted text, optional title, source `paste` and its label, source type, `occurred_at`, a hash of the whitespace-normalised text that is unique per board, status `new | attached | kept | discarded`, the summary, the suggestions as JSON `[{globId, reason}]`, the summary step's state `pending | done | failed` with attempts, `process_after` and `last_error`, the search item it is indexed as, and a version for conditional writes) and `inbox_links` (item and glob, with the attachment it put on the glob; no foreign key to the glob, so deleting a glob removes its links and an item whose last link went becomes `kept`).
- **Pasting:** the *Paste into inbox* dialog (text, optional title, date and source label) and the `add_to_inbox` MCP tool call `InboxService.add`, the one write path (`POST /api/boards/:b/inbox`, 201 `{id, created}`). One transaction stores the row and its knowledge item with chunks, so the text is keyword-searchable at once, even with Bedrock down; the index job embeds the chunks later. Pasting the same text again returns the existing item (`created: false`; text that was discarded comes back as new). Text is limited to 100,000 characters. The item is a `meeting` at paste; the summary step may reclassify it as `thread` or `doc`. All three source types carry the `discussion` authority tier (0.6), below plans and decisions, and are labelled Meeting, Thread and Document in citations. The search sweep (`SearchIndexer.syncBoard`) and glob deletion leave them alone: `InboxService` and `InboxPipeline` own them, and a glob's deletion only removes the glob from the item's links.
- **Summary and suggestions:** `InboxPipeline.processNext` (job `inbox`, paused with `SEARCH_MODEL`) takes the oldest pending item under a two-minute lease and makes one Haiku call, with the text (cut at 30,000 characters) and up to eight candidate globs (open ones found by the title's keywords when a title was given, and by meaning from the title and the start of the text when the embedder works; each with its summary and best matching text). The answer is strict JSON: a title (used only when none was pasted), the kind, a summary of at most 80 words, and up to three suggestions, each a candidate glob with a one-sentence reason; a glob that was not a candidate is dropped. A changed title or kind re-chunks the item once; a finished item is never asked again. While Bedrock is busy or unavailable the item waits with the usual messages and no attempt is spent (growing waits for busy, a minute otherwise); other failures retry with backoff and mark the item failed after three attempts, and it stays listed and searchable without a summary. The pasted text is untrusted: the prompt says so, and the UI shows it as plain text.
- **Inbox page:** an *Inbox* tab beside *Board* (count of new items) lists items newest first with title, source, date, summary (or the start of the text and what it waits for), suggested globs with their reasons and an Attach button each, and the globs it is on. *Attach to...* picks the suggestions and any other open glob; *Keep* and *Discard* settle it. `?item=<id>` (the target of the glob's attachment link) highlights one. Hints (`board.inbox`) refresh the page, and it polls every 15 seconds while an item is being summarised.
- **Attach, keep, discard:** `POST /api/boards/:b/inbox/:id/attach` (`{globIds}`, 1 to 10 globs, all on the board) writes, for each glob not yet linked and in one transaction, a link attachment labelled "From the inbox: <title>" (with the item's number added when another item with the same title is on the glob) through the artifact write path, records the link, and sets the item `attached` and the globs on its search item (no re-chunking). Attaching again changes nothing. `keep` moves a new item to `kept` (still indexed); `discard` removes the item and its chunks from search and is refused while the item is attached, since there is no detach yet. `GET /api/boards/:b/inbox[?status=]` lists (default: new, attached and kept) and `GET .../:id` returns one with its text. All of them are for board members.
- **Context and decisions:** `get_context` gains `inbox`: the items attached to the glob with their summary and text up to 12,000 characters (`truncated` beyond; `search_text` finds the rest). Each attached item is also a decision source on every glob it is on (`inbox:<id>:<glob>`, source kind `inbox`, a decision without a date takes the item's date), so the glob view shows the decisions with a link to the item.
- **Not yet:** detach, a re-run of a failed summary, create-glob from an item, and the other sources.

## Build plan

Slop is built in vertical slices, each usable on its own. The checks above are verified as part of slice 1, and board mockups (card, glob view, System page) are produced at the start.

1. **Foundation and board:** Docker Compose with Postgres, Cognito sign-in, the MCP connector auth checks, globs, the state machine, manual moves and SSE live updates. *Done when:* a signed-in user creates a glob on the board, moves it, and a second browser sees the move live; the Claude app lists it through the MCP.
2. **GitHub App:** provisioning (branch, empty commit, draft PR with labels), webhooks with deduplication, PR and commit awareness, aging, observed merges, the outbox. *Done when:* a glob entering Doing gets a draft PR, and merging it in GitHub moves the glob to Reviewing.
3. **Minimal knowledge delivery:** `get_agent_set`, `sstor init`, the agent set imported from `catalog/agents/`, the knowledge base with the KB catalog, uploads and `import_knowledge` (a project's existing reference docs as the first import), `get_board`, `get_conventions` and a basic `get_context` (plan and attachments only). *Done when:* `sstor init` installs the agents into a fresh checkout and an agent reads a glob's plan and the board's build doc through MCP.
4. **Subs end to end:** intake, routine trigger with run IDs, the routines' agent-set refresh, sub gate, auto-merge, Reviewing with QA. *Done when:* a sub created from the board is implemented by a routine, passes the gate, merges and shows QA Required.
